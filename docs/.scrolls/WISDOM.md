# WISDOM.md

## Constraints — respect and conform to them
- This is a **Design Component** (`.dc.html`): template (`b_dc_html`) + logic class (`c_dc_js`) only. No `<script>` in the template body, no external stylesheets, no class-based CSS — everything inline. Use `dc_html_str_replace` / `dc_js_str_replace` for edits; only use `dc_write` for a full rewrite.
- All styling is inline (`style="..."`) — dark mode works by threading a `theme` object (computed once at the top of `renderVals()`) through `{{ theme.xxx }}` holes, NOT via CSS classes or a stylesheet.
- `{{ }}` template holes are dotted-lookup only — no JS expressions. Anything computed belongs in `renderVals()`, exposed by name.
- `support.js` (the DC runtime) is intentionally left on an older pinned version for this project — do not delete/upgrade it without a specific reason; doing so can change how the whole file renders.
- The only host-Tweaks-panel props are `accentColor` and `wordLevelDiff` — everything else is component state, not a prop. Don't invent new props the component doesn't read.
- No backend. Everything (parsing, rendering, diffing, exporting) runs client-side in the browser. "Shareable link," "Slack export," etc. are honest approximations (data URLs, clipboard, mailto) — never silently imply server-backed functionality that doesn't exist.
- Never clear/overwrite `localStorage`/`sessionStorage` — this project deliberately keeps reviewer state in-memory (not persisted) rather than risk mishandling storage; don't add persistence without re-reading GAP_CONTEXT.md's reasoning first.

## Traps — avoid them always
- **A promise that never settles is invisible to try/catch.** If componentDidMount awaits a Promise.all of async imports and one of them hangs (network stall, CDN issue, circular await) rather than rejecting, the existing try/catch does nothing — the component simply never finishes mounting, and the whole iframe can appear unresponsive (eval_js timing out, no console output) rather than showing a blank div with an error. When debugging "nothing is visible," first check whether the PAGE ITSELF is responsive (eval_js a trivial expression) before assuming it's a data/render bug — a hung page and a component that rendered blank look similar as a bug report but need completely different fixes (a load-timeout/race guard vs. a logic fix).
- **Relationship targets are not all local paths.** parseRelsFor's Relationship entries can be external (TargetMode="External", or an absolute URI scheme like http:/https:/mailto:) — running EVERY target through resolvePath(dir, target) corrupts external hyperlink URLs by prepending the part's directory. Always check TargetMode/URI-scheme before resolving a relationship target as a local path.
- **Don't call `shapeLabel(x)` on a non-text element.** `shapeLabel` reads `x.paras[0]` — images/tables/charts/SmartArt/media objects don't have `.paras`. Use `x.name` for their labels. (This exact bug shipped once — see HANDOFF.md bug #1.)
- **Namespace every diff/decision/comment key.** Element-level diffs are prefixed by kind (`text:`, `image:`, `table:`, `chart:`, `smartart:`, `video:`, `audio:`) via `matchByName(prefix, ...)`. Slide-level keys use `pairKey(aIdx, bIdx)` (`'a'+aIdx+':b'+bIdx`, using `'x'` for null). Per-diff-level keys are `pairKey::diffKey`. Forgetting a prefix/namespace causes decisions/comments to silently bleed across unrelated rows — a bug that won't throw an error, just quietly corrupts data.
- **Watch variable declaration order inside `renderVals()`.** It's one big function; a `const` used before its own declaration line (even inside a closure that only *executes* later) throws a TDZ ReferenceError at the point the object literal containing the closure is CONSTRUCTED, not when the closure runs — e.g. `theme`/`isDark` must be declared before anything that reads `theme.*` in an object literal built earlier in the function. When adding a new computed value, declare it as early as the function's top-level flow allows, especially if multiple sections downstream will reference it.
- **After any multi-line block edit/removal, grep to confirm exactly one definition survives** with sane brace balance. A single deleted line (e.g. a `const x = (...) => ({` opener) can break the *entire* class's `eval` — which fails SILENTLY from the console's perspective in a confusing way ("logic class eval FAILED... template renders with props only"), and every dynamic value on the page goes blank with no runtime exception to grep for. If ALL dynamic values are suddenly blank at once, suspect a syntax error in the JS class first, not a data bug.
- **A second independent `JSZip.loadAsync` of the same buffer, awaited separately from the main parse, is a race-condition risk** on first mount (cold ESM import timing). If you already parsed the buffer once, prefer deriving extra data from that same parse pass, or from data you already know (see the embedded-fonts fix in HANDOFF.md), rather than re-opening the zip a second time.
- **Never assume "works when I manually retest" means "works on first automatic load."** Timing races on `componentDidMount`'s first run are a real, recurring category of bug in this file — always ask "does this depend on anything resolving before something else, without an explicit await chain guaranteeing it?"
- **`src/packages/pptxdiff-vscode/extension.js` has its own copy of the static file server from `bin/cli.js`, not a shared module.** The 2026-07-29/30 CLI security-hardening session (loopback binding, `path.relative()` containment, response headers) fixed only `bin/cli.js`, leaving the VS Code extension's server with the same unbound-`listen(0)` and raw-`startsWith(ROOT)` weaknesses until a follow-up session ported the fixes over by hand. There is no automated check that keeps the two servers in sync — when hardening (or any other logic change) touches one of these two files, check the other for the same pattern before considering the work done.
- **`brew audit` no longer accepts a bare file path** (`brew audit ./Formula/foo.rb` fails hard: "Calling `brew audit [path ...]` is disabled! Use `brew audit [name ...]` instead" — Homebrew/brew#18873). It now requires the formula to live in a tap so it can be addressed by `tap/name`. In CI, stand up a throwaway local tap first: `brew tap-new local/x --no-git`, copy the `.rb` file into `$(brew --repository)/Library/Taps/local/homebrew-x/Formula/`, then `brew audit --strict --online local/x/name`. `brew install --formula <path>` and `brew test <name>` are unaffected — only `audit` changed. Bit `.github/workflows/sync-homebrew-tap.yml`'s `brew-audit` job on its first real run (2026-08-08); fixed by wrapping the path in a local tap.
- **A freshly `tap-new`'d local tap is untrusted by default** (Homebrew's Tap Trust feature, https://docs.brew.sh/Tap-Trust — third-party tap Ruby is unsandboxed code). Referencing a formula by tap-qualified name (`local/x/name`, e.g. right after the fix above) fails with "Refusing to load formula local/x/name from untrusted tap local/x" until explicitly trusted. Fix: `brew trust --formula local/x/name` (narrower than trusting the whole tap with `brew trust local/x`) right after copying the formula into the tap, before `audit`/anything else references it by tap-qualified name. `HOMEBREW_NO_REQUIRE_TAP_TRUST=1` exists to disable the check globally but Homebrew's own docs say not to use it. Second bug found in the SAME `brew-audit` job fix (2026-08-09) — the path-fix alone wasn't enough because switching to a tap-qualified name tripped this separate, newer check; when a Homebrew CLI error changes, re-run for real and check whether a NEW error replaced the old one rather than assuming one fix closes the loop.
- **Homebrew's formula-component style order is enforced by `brew audit --strict`**: `livecheck do...end` must come before `depends_on` (canonical order is roughly desc/homepage/url/version/sha256/license/livecheck/depends_on/install/test — see the audit's own line-number-anchored complaint for the exact expected position). `Formula/pptxdiff.rb` had `depends_on "node"` above `livecheck`; audit failed with "`livecheck` (line 10) should be put before `depends_on` (line 8)" once the tap-trust fix above let audit actually run for real (2026-08-09, third bug found the same day working through this one job — each fix exposed the next real check). None of `lib.mjs`'s regex-based parsing/pin-update logic cares about stanza order, so reordering was a pure formula-file fix with no follow-on code change needed.
- **`brew install` rejects a bare formula path too, not just `brew audit`**: "Homebrew requires formulae to be in a tap, rejecting: ./pptxdiff.rb" — the SAME underlying tap requirement as the `brew audit [path]` deprecation, just enforced by a different subcommand and only reachable once `audit` stopped failing first. Fix is the same shape: install by the tap-qualified name (`brew install --formula local/x/name`) from the local tap already created for audit, not by path. Fourth bug found the same day/session working through this one `brew-audit` job (2026-08-09) — a strong sign these path-based invocations across `brew audit`/`brew install`/(maybe `brew test`, unverified) all trace back to one underlying Homebrew policy change requiring taps, so any future `brew <subcommand> ./x.rb` in this repo's CI should be treated as suspect on sight and written tap-qualified from the start.
- **A literal `</script` substring ANYWHERE in `index.html`'s source text prematurely closes its own outer `<script type="text/x-dc">` tag — including inside a `//` comment or a JS string literal, not just as real markup.** The HTML tokenizer scans raw bytes for that 8-character sequence while in "script data state"; it has no idea it's looking at a JS comment or a quoted string, so a comment that literally says `// a "</script>" tag...` or a self-test fixture string `'</script><img...>'` breaks the WHOLE class's `eval()` (silent per the trap above — "logic class eval FAILED... renders with props only", every dynamic value blank) exactly like a real syntax error would, but the actual defect is upstream of JS parsing entirely (the browser never even got a complete script element to hand to the JS parser). Bit twice in one project: once building the screenshot-export HTML-viewer's generated `<script>` string, again writing THIS trap's own regression self-test (a hostile-input fixture literally containing `</script>` to prove the app's OWN escaping works). Fix is always the same: never let the literal 8-char sequence appear contiguously in this file's source — split it (`'<' + '/script>...'`) or backslash-break it (`<\/script>`, safe in both comments and strings since the tokenizer only matches `<` immediately followed by `/`). After writing ANY string/comment that discusses or constructs script-tag-closing syntax, `grep -i '</script' index.html` and confirm every hit is a real, intentional `<script>...</script>` pair before trusting a green self-test run.

## Ditches — bad patterns or decisions to avoid
- Don't invent an ad-hoc key format for a new export/feature when an existing canonical key scheme already covers that data (e.g. merge-plan export once built its own key instead of reusing pairKey + '::' + diffKey that setMergeChoice actually writes to — silently showed "undecided" for everything). Always trace back to the exact key-building code the setter uses before reading that same state elsewhere.
- Don't build UI via `React.createElement(...)` for anything a user should be able to click/edit in the design surface — write it as template markup. (This file has zero such usage — keep it that way.)
- Don't add a stylesheet or CSS classes for theming "because dark mode would be easier that way." It would violate the DC's inline-style constraint; do the (more tedious but correct) thing of threading `theme.*` holes everywhere instead.
- Don't try to solve "real merge" or "real shareable link" or "real Slack posting" by quietly faking more than what's honestly deliverable client-side — always caveat limitations explicitly to the user rather than let a name like "Export to Slack" imply an integration that doesn't exist.
- Don't hardcode a light-mode color literal as a ternary fallback when adding a new UI element (e.g. `isActive ? accent : '#FBFAF5'`) — always use `theme.card`/`theme.muted`/`theme.border`/`theme.text` for the inactive/neutral branch. This exact mistake caused a dark-mode regression that needed a follow-up fix; audit new code against `grep` for stray hex literals before shipping a "dark mode" claim.
- Don't skip the fallback-safety pass when adding a new per-slide sub-parser (parsing images/tables/charts/notes/etc. from raw OOXML). Wrap each in its own try/catch inside `parseSlide`, with a sane default returned — one throwing parser must never blank out or abort parsing of the rest of the slide/deck.

## Wisdom — best practices and Red/Green TDD
- **Red/Green TDD fixture pattern used in this project**: the sample deck's 2nd slide pair ("Feature Showcase") is RED — an intentional difference planted in *every* diff category in one place, so a single slide pair exercises the whole diff engine at once. The 3rd slide pair ("Stable Slide / control") is GREEN — byte-identical across every category, proving the engine reports zero false positives. When adding a new diff category, extend BOTH: add a deliberate difference to the RED pair AND a matching identical case to the GREEN pair, so regressions in either direction (missed diffs, or phantom diffs on unchanged content) are immediately visible.
- **Build the parser and the sample-data generator together, in the same data shape.** `sample-pptx.js` and the DC's OOXML parsers were co-designed so the generator produces exactly the XML shapes the parser expects — this is why the sample deck can exercise every feature without needing a real, externally-sourced test `.pptx`. Keep this pairing intact: if you add parsing for a new OOXML feature, add a matching generator capability in `sample-pptx.js` in the same change, not later.
- **Prefer graceful degradation over hard failure at every layer**: schematic-render fallback if the fidelity renderer can't parse a part; try/catch-with-default around every per-slide sub-parser; `'—'`/`'(none)'`/`'(unknown)'` fallback text for any field that might be legitimately absent. A diff tool that shows "I couldn't fully compare this" is much better than one that crashes the whole page over one malformed shape.
- **Keep exports honest about their own limitations.** Every export/feature that approximates something bigger (share link, Slack, merge) should say so in its own UI copy or at minimum in this documentation — don't let scope-cuts become silent gaps a future user discovers by surprise.
- **When debugging "looks right on manual retry, wrong on first automatic load,"** suspect timing/races in the mount sequence before suspecting the business logic itself — the logic is often provably correct in isolation (as it was for the embedded-fonts bug); the bug is in *when* something runs relative to something else.

## Wisdom — best practices and Red/Green TDD (addendum)
- When an algorithm has TIES (multiple equally-valid answers by its stated objective), explicitly decide and encode the domain's tie-break preference — don't trust a generic algorithm's incidental tie behavior (patience-sort LIS, stable-vs-unstable sort, first-vs-last match in a greedy scan) to match user expectations. Write the counter-example FIRST (the smallest input that has a tie) as a regression test, then fix the algorithm to pass it — this is exactly how the MOVED-tag bug was finally closed.
- Prefer O(n^2) DP over asymptotically-better patience-sort/greedy algorithms when n is small (here: slide counts, rarely over a few hundred) and the DP lets you carry a secondary tie-break dimension cleanly — the constant-factor/readability win outweighs the asymptotic loss at this scale.

## Wisdom — Red/Green TDD in practice (addendum)
- When asked to 'develop using Red/Green TDD' for several independent features in one turn, the practical approach in this single-file, no-test-runner project is: write each feature's core logic as a PURE, side-effect-free function first (e.g. `buildSlackPayload`, `buildNotionChildren`, `buildConfluenceStorageBody`, `parseReportForImport`) — these are the parts a self-test can actually assert on without mocking network/DOM. Then write the self-test asserting the exact expected shape BEFORE wiring the impure fetch/DOM call that uses it. This gets you real Red→Green value (the pure function either has the right shape or it doesn't, immediately, no network flakiness) even though there's no separate 'run the test suite, see it fail, then fix' round trip available in this authoring environment — the discipline that matters is designing for testability (pure core, thin impure shell), not the literal sequencing of tool calls.
- For any 'live push to an external API' feature, always separate the REQUEST-BUILDING logic (testable, deterministic) from the FETCH CALL itself (network-dependent, environment-dependent success). Test the former; handle failure of the latter gracefully with a clear, specific error message — especially for known CORS-restricted APIs (Notion, Confluence, most REST APIs not designed for direct browser use) where failure is the expected common case, not a bug to chase.
- Never persist credentials/tokens/secrets to localStorage without an explicit user ask, even when the project already persists other state there — call this out in the UI itself so the user isn't surprised either way.

## Wisdom — pure-core pattern, now a house style (addendum)
- This project has now applied the same shape FOUR times across two sessions: extract a pure decision/builder function (no DOM, no network, no localStorage) → write a Red/Green self-test against it → wire a thin impure shell (fetch/DOM/localStorage) around it. Examples: `mergeReportPatch`, `buildConfluenceNewBody`, `interpretSlackDeliveryOutcome`, `buildCredsPayload`, and earlier `buildSlackPayload`/`buildNotionChildren`/`buildConfluenceStorageBody`/`parseReportForImport`. Treat this as the DEFAULT approach for any new feature that touches an external system or has meaningfully complex decision logic — don't inline the decision logic directly into a fetch handler or DOM event handler where it becomes untestable.
- When a browser-only signal is inherently partial (iframe load/error not distinguishing HTTP status, no-cors fetch giving zero signal at all), say so explicitly in both the code comment AND the user-facing message. Never let a partial signal be presented as a full confirmation — 'sent, please verify' is honest; 'delivered' is not, when you can't actually know that.
- When adding ANY new persisted-to-localStorage data, ask first: does this need its own key, separate from existing persisted state? Secrets/credentials always should (this session's `slideDiffLivePushCreds_v1` vs. the existing `slideDiffReviewerState_v1`) so that clearing/opting out of one can never accidentally affect the other.

## Wisdom — generalizing a single-value field into an array (addendum)
- When a second independent fact needs to layer onto an existing single-value UI field (here: MOVED as a lone `secondaryTag` needing to coexist with a new DUPLICATE fact), don't bolt on a second parallel field (`tertiaryTag`) — generalize immediately to an array (`extraTags: [{label,bg}]`) rendered via one loop. The moment you're tempted to add a 'secondary-secondary' field, that's the signal to refactor to a list, even if only two things exist today; a third will come, and a list scales to N while parallel fields don't.
- Parameterizing an existing pure function to add a configurable dimension (`mergeReportPatch(current, imported, conflictWinner)`, `buildCredsPayload(state, fieldsToPersist)`) is almost always preferable to writing a second near-duplicate function — keeps exactly one place to test and reason about the whole decision space, and the default-parameter value preserves old callers' behavior unchanged.

## Wisdom — shared select-all/none helpers (addendum)
- `buildSelectAllMap(keys)` / `buildSelectNoneMap()` are now the established, reused implementation for EVERY multi-select UI in this file (credential fields, batch file rows, reviewer list). If a future request adds another multi-select surface (e.g. selecting multiple diffs, multiple comments), reuse these two functions rather than writing new ones — this is a direct continuation of the 'generalize immediately, don't bolt on a parallel field/function' principle already recorded here.

## Wisdom — scoping confirmation gates narrowly (addendum)
- When asked to add a confirmation step for ONE destructive bulk action, don't proactively add the same gate to OTHER, superficially similar bulk actions unless asked — even if they're also destructive. Respect the literal scope of the ask; note the asymmetry explicitly in GAP_ANALYSIS/GAP_CONTEXT so a future session (or the user) can decide deliberately whether to generalize it, rather than silently expanding scope now.
- When a list's items can be reordered/filtered/mutated, selection state keyed by array INDEX is a latent bug — prefer a content-derived signature/id that survives mutation. This project has now used the same `ts|reviewer|action|label|note` signature shape for both de-duplication (`mergeReportPatch`) and selection (`historySig`) on the exact same history-entry data — one canonical identity function per data shape, reused everywhere that shape needs identity.

## Wisdom — the request/cancel/confirmYes triad (addendum)
- This project now has three identical confirmation-gate implementations (reviewers, comments, history) all shaped as `request*()` (sets a confirm-flag, no-op if nothing selected) → modal renders off that flag → `confirm*Yes()` (performs the action, clears the flag) → `cancel*()` (just clears the flag). Treat this triad as the house pattern for ANY future 'add confirmation before destructive bulk action' ask — don't design a new shape.
- When the confirm-flag needs to carry WHICH scope the action applies to (comments are per-slide, so `confirmDeleteComments` holds the pairKey rather than being a plain boolean), that's fine and expected — the triad's SHAPE stays the same, only the flag's type changes from boolean to 'the scoping id, or null/false when inactive'.

## Wisdom — re-litigating a prior explicit design decision (addendum)
- When a NEW user ask directly contradicts a PRIOR session's deliberate, reasoned decision (recorded in GAP_CONTEXT.md), don't treat the old reasoning as binding — the new explicit ask is the current truth. DO update the old reasoning's entry (or superseding note) so a future session doesn't re-read stale context and get confused about why the code doesn't match the doc. This session's single-comment-delete confirmation is a concrete example: the old 'why it's immediate' reasoning was correct for its moment (avoiding inconsistency) but the user's new ask changed the premises (confirming multiple related actions together resolves the inconsistency concern rather than creating a new one).
- The request/cancel/confirmYes triad has now been proven across 6 destructive actions with zero shape variation — treat any future 'add confirmation before X' ask as a near-zero-design-effort application of this existing pattern, not a fresh design problem.

## Wisdom — collapsing repeated UI into one data-driven block (addendum)
- When the SAME UI shape (a confirm modal, a toast, a badge) is triggered from N different places for N different reasons, don't keep N parallel copies of that UI block once N reaches 2-3 — collapse to ONE block driven by a single piece of state describing 'what to show right now' (here: `pendingConfirm = {title, body, confirmLabel, onConfirm}`), with each trigger site calling a shared opener (`openConfirm`) rather than setting its own dedicated flag. This is the template-side counterpart to the earlier 'generalize repeated pure functions' lesson (buildSelectAllMap, the request/cancel/confirmYes triad) — apply it to STATE SHAPE and TEMPLATE MARKUP, not just to JS helper functions.
- When such a collapse happens, OLD self-tests that asserted against the retired per-action state fields must be REWRITTEN, not left stale — a test referencing a field/method that no longer exists doesn't fail gracefully, it throws and can mask real regressions in the same suite run. Rewriting tests to match a refactor is part of the refactor, not a follow-up.

## Wisdom — the "stale renderVals binding" bug class (addendum, incident-driven)
- **What happened**: the shared-confirmation-modal refactor renamed/removed several methods (e.g. `removeSelectedReviewers` → `doRemoveSelectedReviewers`; `cancelDeleteSelectedComments`/`confirmDeleteSelectedCommentsYes` retired entirely in favor of the generic `closeConfirm`/`confirmPendingYes`), but a couple of `renderVals()` bindings still read `() => this.removeSelectedReviewers()` / `() => this.cancelDeleteSelectedComments()`. Because these are LAZY arrow-function closures, `renderVals()` itself never throws — the dead reference only blows up the moment a user clicks that specific button. This is exactly why the earlier 'grep after any multi-line edit' trap didn't catch it: the eval succeeds, the page renders, everything LOOKS fine until that one interaction path is exercised.
- **The permanent fix**: `checkStaleMethodRefs()` (a static-analysis self-test helper) calls `renderVals()`, walks the ENTIRE returned tree (including nested arrays like `reviewerChips`/`diffs`/`curComments`/`batchListA`/`historyRows`), and for every function value found, regex-scans its `.toString()` source for `this.<name>(` call expressions, checking that `<name>` still exists as a method. This is now the FIRST assertion in `runSelfTests()` — always run it after ANY rename/removal of a method, not just after adding new features. It would have caught this exact incident instantly (RED), without needing to click every button by hand.
- **Rule going forward**: after renaming or removing ANY method, do not consider the refactor done just because the file evals cleanly and the page loads — always also run the self-tests (which now include this static-analysis check) before treating a rename/removal as complete. A clean initial render is NOT sufficient evidence that every button/handler still works; lazy closures hide dead references until clicked.

## Wisdom — auditing for dead/orphaned methods (addendum, incident-driven)
- A method that's DEFINED but never actually CALLED anywhere (`this.methodName(` doesn't appear outside its own definition) is a different bug class from a stale reference to a REMOVED method — it's silent, has no error, and can hide a real functional regression. Found via this exact audit: `restorePersisted()` (the localStorage restore of decisions/comments/history/collapsed-selected-pairs/merge-overrides) was fully implemented and its sibling `restorePersistedCreds()` WAS being called from `componentDidMount`, but the call to `restorePersisted()` itself had been silently dropped at some point — meaning saved reviewer state was written on every change (persistState() calls throughout) but never read back on reload. No console error, no visible symptom except 'my decisions didn't come back after I refreshed' if a user ever noticed.
- **How to audit for this**: extract every method/field name defined on the class, extract every `this.<name>(` call site across the WHOLE file (JS class body, not just renderVals), and diff the two sets. Expect false positives for: constants accessed as properties (not called), lifecycle methods invoked by the host framework itself (`componentDidMount`/`componentDidUpdate`/`componentWillUnmount`), and template-bound class-field arrow functions (resolved directly as instance properties, e.g. `loadSample = () => {...}`, not via `renderVals()`). After filtering those, anything left is either genuinely dead code (safe to delete, e.g. `goPair` was removed as an unused leftover) or a genuine regression (missing call site — fix by adding the call, as with `restorePersisted()`).
- Added a permanent regression guard for the SPECIFIC incident: a self-test asserts `this.componentDidMount.toString().includes('this.restorePersisted()')` — a static source-check rather than re-invoking the lifecycle method (which would unsafely re-run real network/import side effects from inside a test).

## Wisdom — running a browser-only ES module from Node (addendum)
- `sample-pptx.js` is written for the browser (assumes a `JSZip` global, uses `atob`) but has no DOM dependency otherwise — it can run unmodified under plain Node by shimming just those two globals before importing it: `globalThis.JSZip = (await import('jszip')).default; globalThis.atob = (b64) => Buffer.from(b64, 'base64').toString('binary');`. This is how `gen-sample-pptx.mjs` produces real on-disk `.pptx` files from the exact same generator the app uses in-browser, without forking or rewriting any of its logic. Reuse this shim pattern for any future Node-side tooling that needs `sample-pptx.js`'s output (e.g. a future CI fixture-freshness check — see GAP_ANALYSIS.md).
- `jszip` (the Node package) is a generation-time-only `devDependency` for this — it is NOT what the shipped app uses at runtime (the app loads its own vendored `vendor/jszip.min.js` copy in the browser, not the Node package — see SPEC.md §24). Don't confuse the two when reasoning about the "no *npm* runtime dependencies" claim in SPEC.md §21 — that claim is still true (this is dev tooling, and `package.json` still declares zero runtime `dependencies`); it's unrelated to whether the shipped `index.html` itself loads JSZip from a CDN or a local file, which is what §24 changed.

## Wisdom — validating a generated `.pptx` actually opens in real PowerPoint (addendum, incident-driven)
- **"A library opened it" is not "real PowerPoint will open it."** `python-pptx` (and this project's OWN parser, and `@aiden0z/pptx-renderer`) all opened `sample-pptx.js`'s hand-rolled output cleanly — no exceptions anywhere. Real Microsoft PowerPoint still refused to open the same file and couldn't even repair it. Every one of those readers is deliberately lenient (this project's own parser wraps every sub-parser in try/catch with graceful fallback, by design — see the Traps/Ditches sections above); lenient readers cannot be used as evidence that a file is spec-valid, only that it's *readable by lenient readers*.
- **A content-type audit found ONE real defect (SmartArt) but fixing it alone was NOT enough.** `uv run --with python-pptx python3 ...`, using `pptx.opc.package.OpcPackage.iter_parts()` to print every part's `part.content_type` and flag any generic `application/xml` fallback, found that the SmartArt diagram-data parts had no real content type — which led straight to an invented, non-schema `<a:root>` XML underneath. Removing SmartArt from the export was a correct fix for a real bug, but the file STILL didn't open in real PowerPoint afterward — meaning the hand-rolled generator had more than one compliance defect, and validating-and-patching one XML part at a time against a homegrown writer is an open-ended, low-confidence process: absence of evidence (python-pptx found no MORE suspect content types) is not evidence of absence (of some other schema violation python-pptx doesn't check for at all, since it doesn't validate against real OOXML XSDs).
- **The decisive fix was to stop hand-rolling OOXML and use a real writer library instead.** `gen-sample-pptx.mjs` was rewritten around `pptxgenjs` (a proven, actively-maintained npm package purpose-built to produce spec-compliant `.pptx` files) rather than continuing to patch `sample-pptx.js`'s raw-XML-string-concatenation approach. **Rule going forward: for any file meant to be opened by a real, strict, external consumer (not just this app's own tolerant parser) — reach for a battle-tested writer library FIRST, and treat "we'll hand-write OOXML/XML and validate it carefully" as a fallback only when no such library exists**, not a reasonable default even with careful validation, because validation tooling (python-pptx included) is generally just as lenient as the readers it's meant to catch problems for, and will not catch every way hand-rolled XML can violate a spec it doesn't itself enforce.
- Still validate the output either way (walk every object via the high-level API + audit content-types via the low-level `OpcPackage` API, as before) — a real library can still be MISUSED (wrong option shape, missing required field) into producing something odd. The difference is a proven library starts from a much smaller defect surface than a from-scratch XML writer.
- **Case in point**: switching to `pptxgenjs` immediately hit exactly this kind of misuse — `pptx.layout = 'LAYOUT_16x9'` is a real, valid, spec-compliant setting, but its actual dimensions (10 x 5.625in) didn't match what every hand-authored coordinate in the script assumed (13.333 x 7.5in, real PowerPoint's modern widescreen default), so shapes rendered off-slide even though the file itself was perfectly valid OOXML. **Never assume a library's named preset matches the "obvious" real-world value — check the actual emitted dimensions** (`unzip -p file.pptx ppt/presentation.xml | grep sldSz`, converting EMU/914400 to inches) against what your coordinates were designed for, especially when a preset name (`LAYOUT_16x9`) looks like it should be self-explanatory.
- **Standing rule for any script that places many absolutely-positioned elements (position/size math repeated across N call sites)**: add one bounds-check helper (compare `x+w`/`y+h` against the canvas dimensions) and route every placement call through it, rather than trusting each individual coordinate was computed correctly by eye. This is cheap to add once and catches both wrong-canvas-size mistakes (this incident) and ordinary coordinate typos, at generation time rather than as a silent visual defect discovered later.

## Wisdom — vendoring CDN dependencies for offline capability (addendum, this session)
- **A CDN URL can be doing more than "fetch this file" — check what it resolves before assuming a straight download-and-swap works.** `https://esm.sh/@aiden0z/pptx-renderer@1.1.0` wasn't just serving one file: esm.sh transparently rewrites the library's own internal bare-specifier imports (`import "jszip"`) into further CDN URLs at request time. A plain downloaded copy of the library's `dist/*.es.js` still has that bare `import "jszip"` in it, which throws in a browser with no import map. **Fix pattern**: `esbuild --bundle --format=esm` the library's own ESM entry point (installed via `npm install` so its `node_modules` resolution works) into ONE flat file with zero remaining static imports. Dynamic `import(someRuntimeStringVariable)` calls (this library had one, for an optional `pdfjs-dist` PDF-rendering path) can't be bundled by nature — esbuild leaves them as-is; that's fine, it's the same "resolves only if actually reached" behavior the CDN version had too, not a new gap.
- **Before treating "download the pinned version" as a version change, verify it's actually byte-identical to what the CDN served.** `support.js` already had SRI (`integrity="sha384-..."`) hashes pinned for React/ReactDOM from unpkg — recomputing SHA-384 over the freshly-downloaded npm-tarball copies of the SAME version and comparing against those existing hashes confirmed byte-for-byte identity. This means the vendoring swap for those two files was a pure source change (CDN URL → local path), not a de-facto version bump — worth explicitly verifying via existing SRI hashes (or computing new ones) whenever a "vendor this exact CDN-pinned version" task claims not to be changing behavior.
- **A pure static-analysis Node script is a legitimate Red/Green TDD vehicle for an infrastructure-level change that has no interesting pure function to unit-test.** This app's usual TDD pattern (WISDOM.md's "pure-core-first" rule) doesn't apply well to "stop loading these 5 URLs from a CDN" — there's no business logic to extract. `src/pptxdiff/test_offline_capable.mjs` instead asserts a testable INVARIANT (no known-CDN-host string appears in the served files; every local vendor reference resolves to a real file on disk) — genuinely RED against the pre-vendoring code (5 failing checks, one per CDN host actually in use) and genuinely GREEN after. This is the same spirit as `test_gen-sample-pptx.py`'s content-type/geometry audit: a script-based regression check for something a browser self-test can't easily express, checked into the repo as a permanent guard (unlike the one-off Playwright smoke test below).
- **A live-browser smoke test with network blocked is the strongest available proof vendoring actually works, but keep it out of the repo unless it's made robust/CI-friendly.** After the static swap, a throwaway Playwright script (pattern: block every `route` whose URL isn't the local server / `data:` / `blob:`, then load the page, run the app's own `runSelfTests()`, and upload the real on-disk `.pptx` fixtures) caught a REAL verification bug: an early version of the check used a case-sensitive `/RENDERED/g` regex against page text, which never matches this app's actual title-case "Rendered" badge text — silently reporting 0 rendered badges as if the vendored renderer were broken, when it wasn't. Prefer exact element/text queries (`page.getByText('Rendered', {exact:true})`) over regex-scanning the whole page body for anything case-sensitive-fragile. This script was NOT checked in (matches this project's precedent — HANDOFF.md's earlier Puppeteer validation round was also "install temporarily, use once, remove," not a permanent devDependency) since it needs a running server + browser + real fixture files to mean anything, unlike `test_offline_capable.mjs` which is a pure static check safe to leave as a standing regression guard.
- **Font vendoring means giving up automatic `unicode-range`-based subset negotiation — decide the subset deliberately, don't ship everything "to be safe."** Google Fonts' CSS response serves ~6 different files per weight (one per Unicode range: latin, latin-ext, cyrillic, cyrillic-ext, vietnamese, greek), each gated by an `@font-face`'s `unicode-range` so the BROWSER only downloads the one covering text actually being rendered. A vendored `@font-face` has no such negotiation — it's just an unconditional local file. Shipping only the subset the app's actual UI needs (here: latin, since the app is English-only per the existing i18n gap) is the honest choice over reflexively vendoring all ~24 files "just in case"; document the tradeoff (non-Latin text falls back to the browser default) as a gap rather than silently dropping coverage.
- **Regenerating the vendored `pptx-renderer.bundle.js` if the pinned version ever changes**: `npm install --no-save @aiden0z/pptx-renderer@<version> jszip@3.10.1 esbuild@<version>` in a scratch directory, write a one-line entry file (`export * from "@aiden0z/pptx-renderer";`), then `npx esbuild entry.mjs --bundle --format=esm --platform=browser --target=es2020 --outfile=pptx-renderer.bundle.js`. Sanity-check the result with a plain Node dynamic `import()` of the output file (no DOM needed — the top-level module code doesn't touch `window`/`document` until its exported classes are actually instantiated) and confirm `parseZip`/`buildPresentation`/`PptxViewer`/`RECOMMENDED_ZIP_LIMITS` are all present in the export list before treating the rebuild as done.

## Wisdom — leftover trailing fragments after replacing a function body (addendum, incident-driven)
- When using `str_replace_edit`/`dc_js_str_replace` to insert a NEW function between two EXISTING ones, double-check the tail of your `old_string`/`new_string` boundary — if the old text you matched ended mid-way through the neighboring function's shared closing lines (e.g. `return out;\n  }`), the replacement can leave a stray orphaned `return out;\n  }` sitting AFTER your new function's own closing brace, silently producing `SYNTAX ERROR: Unexpected identifier 'out'` (or similar) at the whole-class level. This happened when `findCrossDeckDuplicates` was extended and `sectionForSlideIndex` was inserted after it — the old function's trailing `return out;\n  }` survived past the new function boundary.
- **Mitigation**: after inserting/replacing a function via a partial-body edit, always read the ~15 lines immediately following your new function's closing brace and confirm the NEXT method starts cleanly — don't just trust that the edit tool reported success (it did; the edit was applied exactly as instructed, the bug was in the boundary I chose, not the tool). This is a sharper, more specific case of the pre-existing 'after any multi-line block edit, grep to confirm exactly one definition survives' rule — here the fix is to also check the few lines immediately AFTER the new code, not just that the new code's own definition is intact.

## Wisdom — building the `docs-site/` (MkDocs), two gotchas worth remembering (addendum)

## Wisdom — adding a runtime toggle to a static, no-build-step app (addendum, `PPTXDIFF_LITE_MODE`)
- **An OS environment variable is only ever visible to the Node process — design the browser-side mechanism FIRST, then treat the env var as a convenience wrapper around it.** `PPTXDIFF_LITE_MODE` can only be read by `bin/cli.js`; the actual runtime decision has to live somewhere a browser can see it. The right shape here was: `bin/cli.js` translates the env var into a URL query param (`?lite=1`) it opens the browser at, and `support.js` (the very first script the page loads) parses that param once via `location.search` and exposes the decision as `window.__PPTXDIFF_LITE_MODE__` for everything else on the page to read. Don't reach for the tempting-but-wrong shortcut of having the Node server inject a `<script>` tag into the HTML response server-side to "pass the env var into the browser" — it works, but it silently breaks a documented invariant (`bin/cli.js` "serves files unchanged," per `architecture.md`) for a problem the query-param approach already solves cleanly, with the bonus that non-CLI usage paths (opening the file directly, an editor extension with no Node process) get a manual override for free.
- **DC helmet content (`<link>`/`<script>` tags outside the reactive template) can't hold a runtime-computed `src`/`href` via a `{{ }}` hole** — those holes are dotted-lookup only (no JS expressions), and helmet's own `compile()` in `support.js` just clones the child element's static attributes verbatim (see `createHelmetManager`). To make a helmet tag's URL a runtime decision, replace the static tag with a small inline `<script>` (no `src`) that does its own `document.createElement('link'/'script')` + `appendChild` — verified this actually executes (unlike assigning HTML via `innerHTML`, which browsers never execute embedded `<script>` tags from) by reading `compile()`'s SCRIPT branch: it creates a real `<script>` element via `doc.createElement`, sets `.textContent` from the source node's text, THEN appends it to `<head>` — that specific sequence (create → set text → insert) is what makes an inline script actually run, and was confirmed empirically already working pre-lite-mode (the vendored JSZip `<script src>` tag in the same helmet block was already going through this exact path).
- **When a Red/Green test's core invariant becomes intentionally false by design, rewrite the test rather than special-case around it.** `test_offline_capable.mjs` previously asserted "these CDN host strings must never appear in the source" — implementing lite mode as an opt-in, correctly-gated CDN fallback makes that assertion actively wrong (the strings NEED to be there now). Weakening it (e.g. "must not appear unless near a lite-mode check") would have been more fragile than just replacing it with the actual invariant now in force: default-vendor-path present AND CDN-fallback present AND both reachable only through the flag. Treat "the feature I'm building makes an existing test's premise false" as a signal to redesign that test's assertions, not to bolt on an exception.
- **Verifying a network-sourcing toggle in a sandbox with restricted egress**: when the CDN hosts a "lite mode"-style feature targets are themselves blocked by the sandbox's own outbound proxy (confirmed here via a plain `curl` returning `CONNECT tunnel failed, response 403` for `unpkg.com`/`esm.sh`/`cdnjs.cloudflare.com`, but 200 for `fonts.googleapis.com`), don't try to force a full successful end-to-end load as the bar for "verified." Instead assert the NARROWER, still-meaningful claim: capture the actual request URLs the browser attempted (Playwright's `page.on('request', ...)`) and confirm they target the right hosts — a `net::ERR_TUNNEL_CONNECTION_FAILED` on an otherwise-correctly-addressed request is the sandbox's network policy, not a bug in the code being tested. Cross-checked this reasoning by also capturing console/pageerror output and confirming the failure mode matched the code's own existing error handling (`support.js`'s `loadReactUmd().catch(...)` logging exactly the expected message) rather than some other, unexplained failure.

## Wisdom — building a documentation-coverage tracker with Jinja page-content rendering (addendum, this session)
- **`mkdocs-material` alone does NOT Jinja-template page bodies — only the theme.** This is easy to get wrong: MkDocs uses Jinja2 internally, but only for rendering the HTML *theme* around your content; `{{ }}` typed into a `.md` file's body is inert by default, just literal text. Real Jinja-in-Markdown (variables, loops, macros reading front matter) needs `mkdocs-macros-plugin` as an explicit added dependency — there is no way to get this from Material's own feature set.
- **Before turning on any plugin that Jinja-processes markdown bodies, grep the whole docs tree for the delimiter it will interpret.** This project's own app (`index.html`) uses `{{ theme.border }}`-style DC template syntax as its literal authoring language — if any docs-site page ever quotes that syntax in prose or a code block, a naively-configured macros plugin would try to evaluate it as a Jinja expression and fail the build (or worse, silently substitute garbage). Checked first (`grep -rn '{{' docs-site/docs/` — zero real hits, two binary-file false positives from PNG bytes) and, more durably, set `render_by_default: false` in `mkdocs.yml` so Jinja rendering is opt-in per page (`render_macros: true` in that page's own front matter) rather than applied everywhere by default. This means the risk stays permanently closed even if a FUTURE page quotes the app's `{{ }}` syntax, not just as of today's grep.
- **Read a macro's front-matter data straight from disk inside the macro function, rather than depending on the plugin's "current page" API.** `mkdocs-macros-plugin` does expose ways to reach the in-progress page's `meta` from within a macro, but the exact mechanism is an implementation detail of the plugin version installed. Since this coverage page's data has exactly one producer (`sync_doc_coverage.py --write`) and exactly one consumer (this one page, always), `main.py`'s macros just re-parse `documentation-coverage.md`'s own front matter directly with the same front-matter-splitting logic as the sync script, once, at `define_env()` time — simpler, and doesn't depend on details of the plugin's internal API surface holding steady across versions.
- **A coverage/measurement tool's SCRIPT is the "test"; its generated CONTENT is not something to game.** `sync_doc_coverage.py --check` is a real Red/Green regression test (structural integrity + staleness — dangling ids, broken anchors, duplicate registry entries, drift between disk and a fresh scan) that was verified by deliberately breaking three different things and confirming each was caught with a specific message before fixing them back to GREEN. But the actual *coverage numbers* it reports (25/33 complete) are a measurement, not a test assertion — there is no "must be 100%" check, and the session that built the tool did not pad the numbers by rush-writing content for the 8 gaps it found in the same sitting. Keep these two things conceptually separate in any future measurement/coverage tool: verify the MEASURING INSTRUMENT is correct (that's the test), and report whatever it measures honestly (that's not something to test against a target).
- **Give every registry item's human-readable label exactly one home.** `coverage_registry.yml` owns `title`; every page's `doc_coverage:` entry references an `id` only. This was a direct, deliberate response to a user question during design ("does front-matter `title:` reflect what you want shown on the page?") that surfaced a real risk (accidentally duplicating/mismatching title strings across many files) before any code existed — worth remembering as a general pattern: when a new front-matter key is about to be added at scale across many files, ask specifically which OTHER meaning that key (or a same-named one) might already carry in the templating system you're building on, before assuming a blank slate.

## Wisdom — capturing real screenshots/GIFs of a running app for docs (addendum, this session)
- **Screenshot the REAL app via Playwright, not a recreation.** Every image added to `docs-site/` this session came from actually driving `bin/cli.js`'s served app (add a reviewer, click Batch, upload the real `docs/assets/sample_*.pptx` fixtures, open the Export dropdown) rather than a hand-styled mockup — the difference matters for documentation specifically, where a screenshot is implicitly a claim "this is what you'll actually see," not a design proposal (contrast with the earlier "Offline Mode" mockup, which explicitly WAS a proposal and said so).
- **A generic `xpath=ancestor::div[N]` locator for "the panel containing this text" is fragile — check what it actually captured, don't assume.** Several attempted "crop to just this panel" screenshots this session (`app-diff-list`, `app-merge-preview`, `app-reviewer-bar`) ended up capturing the whole page instead of a tight panel, because the DOM nesting depth didn't match the guessed ancestor count. Rather than fight increasingly-specific selectors, the pragmatic fix was to just accept the full-page capture where it was still genuinely informative (it was, in every case here) — a slightly-too-wide real screenshot beats a brittle selector that might silently crop wrong.
- **When batch-uploading real files fails a `setInputFiles` locator, check what attribute actually survived the templating runtime — don't assume the DOM matches the source.** `input[type="file"][multiple]` matched zero elements even though the source markup clearly has `multiple` on those inputs — this project's DC runtime (`support.js`) strips the `multiple` attribute when copying it into the live DOM (confirmed by dumping every file input's `outerHTML`). The working fix was scoping by an attribute that DOES survive (`label:has-text("Before files") input[type="file"]`), not fighting the missing one.
- **Before committing to a "record the interaction, convert to GIF" plan, capture once and inspect the actual frames — don't assume the interaction has enough visual duration to be worth animating.** The offline-mode-toggle GIF was recorded, converted, and only THEN discovered (by sampling a background-color pixel across every extracted frame) to be ~25 frames of idle light-mode UI followed by an instant jump to a blank page — the real page navigation this app's toggle triggers happens faster than its own 180ms CSS transition can render in a local dev environment. Cheap diagnostic for any future "does this GIF actually show what I think it shows" question: extract frames, sample one representative pixel per frame, and print the sequence — far faster than eyeballing dozens of frames individually, and it makes a "it's just idle time then a jump cut" problem obvious immediately.
- **This sandbox's `ffmpeg` build (Playwright's bundled copy) has NO gif encoder/muxer and NO `fps`/`palettegen` filters** — it's a minimal `--disable-everything`-then-selectively-enabled build meant only for Playwright's own webm screen-recording, not general transcoding (confirmed via `-muxers`/`-codecs`/its own `-version` config string). Workaround: use it only for what it CAN do (decode the recorded webm + `scale` filter + emit a PNG sequence via `-r <fps> out/f%03d.png`), then hand the PNG sequence to Pillow (`Image.save(..., save_all=True, append_images=..., duration=..., loop=0)`) for the actual GIF encoding — Pillow needs no ffmpeg at all for that step.
- **`uv run --with <pkg> python3 ...` (no `--only-group`) resolves the ROOT project's dependencies too**, same trap as `uv run --group docs` documented in `DOCS.md` — it happened again here (pulled in `torch`/CUDA packages to get Pillow) and happened to succeed quickly only because most of it was already cached from an earlier invocation in the same session. For a one-off "I just need library X" script unrelated to any dependency group, prefer `uv run --no-project --with <pkg> ...` (or an isolated `uv run --isolated`) to avoid resolving the root project at all.

## Wisdom — turning the above into a committed, reusable capture script (addendum, a later session)
- **A "blank first frame" from Playwright video recording is not one fixed-size artifact — measure it, don't guess a constant.** `context.recordVideo` starts capturing at context creation, before the page's first real paint, so the opening frames of any recording are blank canvas — but how MANY varied 3-4 frames across otherwise-identical runs of the exact same scenario. An earlier fix that unconditionally dropped exactly one leading frame (`frame-0001.png`) left 2-3 blank frames still in the GIF. The robust fix: a content-based heuristic (downsample each frame, greyscale, average brightness > 250 ⇒ blank) that drops leading frames until a real one is found, whatever that count turns out to be on a given run. Same underlying diagnostic instinct as the offline-mode-toggle lesson above (sample pixels across frames, don't eyeball) — worth treating as the general pattern for "does this video-derived asset actually start where I think it starts."
- **A full-viewport GIF can be several times larger than a hand-curated tight crop, for no gain in what it actually communicates.** A first automated pass at the dark-mode-toggle GIF used the same 1280×900 viewport as the PNG screenshots and came out to 2.6MB, vs. the original hand-captured asset's 963KB at a 720×208 header-only crop. The fix was adding per-scenario `viewport` override support (`newContext({ viewport: scenario.viewport || DEFAULT })`, applied to both the context AND `recordVideo.size`) rather than a single global viewport constant — a GIF documenting one small interaction (a toggle click) only needs to show the region where the visible feedback actually happens, not the whole page. Brought the file down to 841KB, comparable to the hand-curated original.
- **Node's ESM `import` resolution ignores `NODE_PATH`; only CommonJS `require()`'s resolution algorithm honors it.** A sandbox with `playwright` installed only globally (via `NODE_PATH` pointing at a global `node_modules`) will hard-fail a top-level `import "playwright"` in an `.mjs` file with `ERR_MODULE_NOT_FOUND`, even though the exact same package resolves fine via `require("playwright")`. Fix: resolve just that one dependency via `require()` obtained from `createRequire(import.meta.url)`, keeping everything else in the file as ordinary ESM `import` for Node builtins — the two module systems can coexist in one `.mjs` file this way. Relevant any time a script needs to reach an intentionally-not-a-project-dependency package (see `capture_screenshots.mjs`'s header comment for why `playwright` is deliberately not in `package.json`) that might only be available via `NODE_PATH` in some environments.
- **A live browser's serialized `style` attribute is not the source HTML's `style="..."` string, byte for byte.** An xpath locator written against `contains(@style,'border-radius:12px')` (matching `index.html`'s source exactly, no space after the colon) silently matched zero elements — the browser normalizes the attribute once parsed into the live DOM (`border-radius: 12px`, space added) and `getAttribute('style')` reflects that normalized form, not the original source text. Confirmed by dumping `getAttribute('style')` at each DOM ancestor level rather than assuming the source and the live DOM agree. Any selector built by eyeballing `index.html`'s source for a style-attribute substring needs to account for this normalization, not just copy the source text.

## Wisdom — the CommonJS entrypoint guard, applied to `bin/cli.js` (addendum, security-hardening session)
- The `capture_screenshots.mjs` ESM entrypoint guard (`if (process.argv[1] === fileURLToPath(import.meta.url))`) has a direct CommonJS equivalent: `if (require.main === module) { ... }`. Used this to make `bin/cli.js`'s pure `buildBrowserOpenCommand(platform, url)` helper importable/unit-testable without the side effect of actually starting the real static server — when a CJS file is loaded via a dynamic ESM `import()` from a test script (rather than run directly as `node bin/cli.js`), `require.main` is `undefined` inside it (there's no CJS main module when the process entrypoint is ESM), so the guard correctly skips the server-start/browser-open block. Same underlying principle as the ESM case: a self-executing script becomes testable by guarding its own execution, not by splitting into a separate always-imported library file.
- When exec-vs-execFile matters for shell-injection hardening, the strongest test isn't just "does the source contain the word execFile" (a static grep) — it's asserting the pure command-builder passes a shell-metacharacter-laden string through as ONE untouched argv array element (proving no shell interpolation is possible), on every platform branch, including the Windows one (`cmd.exe /c start "" <url>` — `start` is a cmd.exe built-in, not a standalone executable, so it must be routed through `cmd.exe` rather than `execFile("start", ...)` directly).

## Wisdom — verify a "known weakness" is actually reachable through the specific call site before testing for it (addendum, security-hardening session)
- `path.normalize()` on an already-absolute string (leading `/`) clamps `..` at the root — it can't produce a result that still starts with `..`. `path.join(root, laterArg)` does NOT treat a leading `/` in `laterArg` as an absolute-path reset (unlike `path.resolve()`) — it just concatenates segments. Combined, `path.join(ROOT, path.normalize(reqPath))` in `bin/cli.js`'s request handler already prevented `../`-style HTTP traversal from escaping `ROOT` *by construction*, before the containment check (`startsWith(ROOT)` or its `path.relative()`-based replacement) even runs — confirmed with a plain `node -e` trace comparing several traversal payloads against both forms.
- This mattered concretely when writing `test_path_containment_cli.mjs` for the `isPathContained()` hardening (P0 ticket 3): an HTTP-level test asserting the old code returned `403` for `../../../etc/passwd` was simply wrong — it returned `404` (the resolved-but-still-contained path just doesn't exist), both before and after the fix. The actual, meaningful `startsWith()`-vs-`path.relative()` divergence (a sibling directory sharing `ROOT`'s prefix, e.g. `/app/pptxdiff-evil`) isn't reachable through this call site's `path.join(ROOT, ...)` construction at all — a `path.join` can't literally produce a `ROOT + "-evil"` string, since it always inserts a separator. That case is only testable by calling the pure containment function directly with a crafted sibling path.
- **Rule going forward**: when a security-analysis doc describes a weakness in a *check function* in the abstract, don't assume every call site that uses that check is actually exploitable via that weakness — trace the specific data flow (here: `decodeURIComponent` → `path.normalize` → `path.join` → containment check) with real inputs before writing the regression test, and write assertions that match what's actually true of the code (e.g. "never leaks a 200" rather than a specific status code you haven't verified), while still hardening the check itself as defense-in-depth for cases that ARE reachable elsewhere or in the future.

## Wisdom — a manifest + doc file, kept honest by cross-checking each other (addendum, security-hardening P1)
- When provenance/config data needs BOTH a machine-checkable form (a script reads it) AND a human-readable form (a person reads it), don't just write both and hope they stay in sync — have the verification script assert the human doc CONTAINS the machine manifest's own values (here: `verify_vendor.mjs` checks that every `manifest.json` hash string literally appears in `PROVENANCE.md`). This is cheap (a substring check) and turns "the prose doc quietly went stale after the next vendor bump" into an immediate, loud CI-style failure instead of a silent drift someone notices months later.
- **Reuse an existing hardcoded value as a cross-check rather than treating it as unrelated.** `support.js` already hardcodes sha384 SRI hashes for React/ReactDOM (for the CDN/lite-mode `<script integrity="...">` tags) — `scripts/verify_vendor.mjs` re-derives sha384 for the vendored copies and asserts they match those existing constants. This is the same "prove two independently-arrived-at values agree" technique as the original vendoring session's one-off manual check (see the vendoring addendum above), just made permanent and automated instead of a one-time verification note in `HANDOFF.md`.
- **A provenance/manifest checker is validated by deliberately corrupting BOTH what it checks AND what it checks against, not just one.** Two separate RED demonstrations were needed to actually prove `verify_vendor.mjs` works: corrupting a hash *inside `manifest.json`* (proves the manifest-vs-doc drift check works) and corrupting a byte in *the real vendored file on disk* (proves the manifest-vs-disk hash check, AND the sha384-vs-`support.js` cross-check, both work) are different failure modes and neither alone proves the other path is wired correctly. Always restore from an explicit backup copy (`cp file /tmp/backup` before mutating) and confirm via `git status`/`git diff` that the restore is byte-identical to the tracked copy — don't just trust that re-running whatever generated the file originally will reproduce it exactly.

## Wisdom — staging + pixel-level compare-and-promote for generated screenshots (addendum, a later session)
- **Compare decoded pixels, never file bytes/hashes, when the question is "did the CONTENT change."** Confirmed empirically before designing anything: two Playwright screenshots of the identical app state, captured seconds apart, were byte-IDENTICAL in this environment (nothing to worry about there) — but the currently-committed hand-captured assets from an earlier session had genuinely different pixels for reasons unrelated to encoding (see below), and separately, resaving the exact same pixels through Pillow with different `optimize`/compression settings produces different bytes for identical pixels. A byte-hash-based "did it change" check would be right in the common case and wrong in exactly the cases that matter (silently promoting a no-op due to encoder noise, or silently trusting a byte-identical-but-corrupt file). Decode-and-compare (`compare_images.py` via Pillow) is barely more code and closes both failure modes at once.
- **Before trusting an image diff, use it to investigate an existing surprising diff — it may reveal a real bug in an unrelated part of the pipeline, not just validate design choices.** Pixel-diffing the old hand-captured `export-menu.png` against a freshly automated one (as a sanity check on the comparison approach) surfaced a ~6% differing-pixel region — not encoder noise, but a real behavioral difference: the old hand session's browser tab had accumulated reviewer state (`@alex` added) via shared `localStorage` across several manually-captured scenarios in the same tab, while the new automated script gives every scenario a fresh, isolated `browser.newContext()`. The pixel-level comparison didn't just validate the tool, it caught that the OLD asset had unintentional cross-scenario state leakage baked into it — worth remembering: an "unexpectedly large diff" during a tooling sanity check is itself a signal worth chasing down, not just a number to note and move past.
- **Not all captures are equally deterministic — measure before assuming a uniform comparison policy will behave uniformly.** Two consecutive runs of every PNG scenario in this project's `capture_screenshots.mjs` produce byte-identical output (Chromium's screenshot encoder is fully deterministic for a static, already-settled page render). The one GIF scenario does NOT: two consecutive runs of the identical interaction produce GIFs with the same frame count but measurably different pixels in the mid-transition frames, traced to the recorded `.webm`'s lossy encoding plus real-wall-clock timing jitter in exactly when each frame lands relative to the CSS transition's 900ms window (confirmed by sampling one pixel per frame across two runs — steady-state frames matched, transition frames didn't). Consequence for any "only promote on a real change" workflow: a pixel-perfect comparison will report a false-positive "changed" on essentially every rerun of a video/GIF-derived asset, even with zero real change, while the same comparison is exactly right (zero false positives, zero false negatives) for static screenshots. Don't paper over this with a blanket fuzzy-match tolerance unless asked — that trades away the ability to detect a REAL visual regression in exchange for hiding a known, well-understood, harmless one. Document the asymmetry plainly instead (see DOCS.md §11) so nobody is surprised later that "unchanged" means something slightly different for a GIF scenario than a PNG one.
- **A CLI script becomes unit-testable by guarding its own execution, not by extracting a separate library file.** `capture_screenshots.mjs` needed its `SCENARIOS`/`syncStagedFileToTarget`/etc. to be `import`-able by test files without triggering a live Playwright/server run just from the `import` statement (ES modules execute top-level code on import). Fix: `export` the pieces worth testing, and wrap the unconditional `main().catch(...)` at the bottom in `if (process.argv[1] === fileURLToPath(import.meta.url)) { ... }` (the standard "was this the entrypoint or an import" check for a `.mjs` file, no `require.main === module` equivalent exists in ESM). Cheaper than splitting into a separate always-imported module, and keeps one file as both a working CLI and a testable library.
- **A genuinely useful test suite for an orchestration function doesn't need to run any of the expensive things it orchestrates.** `test_sync_staging_to_target.mjs` tests real promotion logic (`syncStagedFileToTarget`) using the REAL `compare_images.py` (not a mock — mocks can silently drift from what the real comparator does) against tiny synthetic Pillow-generated fixture images — no Playwright, no browser, no `bin/cli.js` server, runs in a couple seconds, works identically with or without `NODE_PATH`/Playwright installed at all. The expensive, non-deterministic, environment-dependent part (driving a real browser through a real scenario) stays a manual/by-hand verification step (see DOCS.md's precedent of "verified for real" sections) rather than something the committed automated test suite depends on — matches this project's established split between fast checked-in regression tests and throwaway/manual E2E Playwright verification (see the `WISDOM.md` entry on `test_offline_capable.mjs`'s sibling smoke test, never checked in, above).

## Trap — an SVG `<foreignObject>` unconditionally taints any `<canvas>` it's drawn onto (found building the screenshot-export feature, this session)
- Building an in-app "download screenshots" feature, the obvious technique for capturing a live DOM element as an image with zero new dependencies is: clone the element, serialize it into an SVG `<foreignObject>`, draw that SVG onto a `<canvas>` via `drawImage()`, then call `canvas.toDataURL()` for real PNG bytes. This works for steps 1-3 (the SVG itself renders perfectly, confirmed by opening it directly) but **step 4 always throws `SecurityError: Tainted canvases may not be exported`, in Chromium, unconditionally** — reproduced with a trivial plain-text foreignObject SVG containing zero images, zero canvases, zero cross-origin anything. This is a deliberate browser security policy (foreignObject can embed arbitrary HTML that could reference resources the browser can't fully vouch for), not a bug in the SVG's content, and there is no workaround for it within this technique.
- **Don't assume "it renders fine when I look at it" means "I can also read its pixels back out."** These are two completely different privilege levels in the browser's security model. Displaying an SVG (via `<img>`, inline in a page, or a browser tab) is unrestricted. Reading pixel data back out of anything that SVG touched (via `canvas.toDataURL()`/`toBlob()`/`getImageData()`) is a separate, much more restricted operation — confirm which one your feature actually needs before assuming a rendering trick will also give you exportable bytes.
- **The fix wasn't to work around the wall — it was to stop needing to cross it.** Rather than vendor `html2canvas` (which exists specifically to avoid this exact wall, by re-implementing CSS rendering with plain canvas 2D drawing primitives instead of ever routing through an SVG image) or hand-roll an equivalent, the shipped feature ships the SVG *itself* as the downloadable artifact instead of a rasterized PNG. Zero new dependencies, and it sidesteps the restriction entirely since the restriction is only on the canvas-readback step, which the feature no longer performs. Worth remembering as a general pattern: when a technique hits a hard platform wall at the very last step, check whether the intermediate artifact (here, the SVG) is already a legitimate, useful end product on its own before reaching for a heavier dependency to push through the wall.
- **Verify a suspected browser-security wall in complete isolation before redesigning around it.** The first sign was a real in-app failure with a confusing stack trace; before concluding "this technique is fundamentally blocked," a minimal 15-line repro (blank page, inline SVG string, zero app code) confirmed the exact same throw with the simplest possible content — ruling out "something in pptxdiff's own DOM is uniquely tainting this" and confirming "this is unconditional for ANY foreignObject-bearing SVG." Don't debug/work around a platform restriction against your full app when a 15-line isolated repro answers the question faster and more conclusively.

## Trap — React sets inline styles via the DOM `style` property, not an HTML `style="..."` attribute (found building `pptxdiff-cli`'s browser-automation shim, this session)
- Building the headless CLI/API's automation layer (`lib/automation.js`, driving the real app via `playwright-core`), the obvious way to detect this app's error banner (`<div style="background:#FBEFEC;...">` in the template source — everything here is inline styles, per this file's own Constraints) was a CSS attribute selector: `div[style*="#FBEFEC"]`. It never matched, in any test, however long the wait — even though direct instrumentation proved the error state WAS being set correctly (`inst.state.errorMsg` had the right value; the text was genuinely in `document.body.innerText`). Root cause, confirmed directly: `element.getAttribute('style')` on the rendered banner returns `null`. React applies inline styles via the DOM `style` PROPERTY (a live `CSSStyleDeclaration`, set via the style object's own setters), not by writing an HTML `style="..."` ATTRIBUTE string — so there is no attribute for a `[style*="..."]` CSS selector to match, for ANY React-rendered inline-styled element in this app, not just this one banner.
- **Don't trust `document.body.innerText`/`getAttribute` results near an inline-styled React app to reveal "no such element" — verify what's actually failing before concluding the underlying app logic is wrong.** Every debugging instinct pointed at the app (does `onUpload` actually run? does the rejection actually propagate? does `setState` actually trigger a re-render?) before the real, much simpler answer (the SELECTOR itself could never match anything, ever, regardless of app behavior) was found — by literally calling `element.getAttribute('style')` and getting `null` back. When a selector-based detector reports "not found" for something independently proven to exist in the DOM, suspect the selector's fundamental assumption about how the framework writes that DOM, not the app's business logic, especially a few debugging rounds in.
- **The fix: `getComputedStyle(el).backgroundColor`, not an attribute selector.** Browsers normalize `getComputedStyle()`'s color output to `rgb(r, g, b)` regardless of how the color was originally specified (hex, named, rgb()), so `Array.from(document.querySelectorAll('div')).find(d => getComputedStyle(d).backgroundColor === 'rgb(251, 239, 236)')` reliably finds the banner. Any future Playwright-driven automation of this app needing to detect a specific inline-styled element should reach for computed style, not an attribute selector, from the start.
- **The debugging path that actually found it**: React fiber traversal (`element[Object.getOwnPropertyNames(element).find(k => k.startsWith('__reactFiber$'))]`, walking `.return` up to a `stateNode`) to grab the live component instance directly and call its methods/read its `.state` bypassing the DOM entirely — this is what proved the APP was correct (state genuinely held the right error message) before the selector bug was found. Note this project's DC runtime wraps the logic class in a `StreamableComponent` wrapper (`support.js`) — the instance you want is `fiber.stateNode.logic`, not `fiber.stateNode` itself (the wrapper), and fiber keys are non-enumerable (`Object.keys()` won't find them — use `Object.getOwnPropertyNames()`).

## Trap — a naive "readiness" wait for this app can be satisfied by its OWN initial/default state, not real data (found building `pptxdiff-cli`'s automation shim, this session)
- The app boots with a default sample deck already loading on BOTH sides (`componentDidMount()`'s `buildSample()`, calling `ingest('A', ...)` then `ingest('B', ...)` sequentially) — and the "Differences (N)" panel header can render from the CONSTRUCTOR's initial (effectively empty) state before that async load has even started. A readiness check that waits only for that text to appear is satisfied almost immediately after `page.goto()`, well before real data has loaded — so uploading a real file right after "looks ready" races the default sample's own still-in-flight `ingest()` calls, and whichever `setState` call lands LAST wins, silently overwriting the just-uploaded data. Caught via a genuine RED failure: `diffDecks(sample_before, sample_before)` (same file both sides — should show zero differences) intermittently reported real differences, and the exported report's `deckBefore` sometimes came back as the DEFAULT sample's name instead of the uploaded file's.
- **The fix: wait on the LAST thing each side's `ingest()` sets, not the first UI element that happens to render early.** Each side's parser-independent content checksum (SPEC.md §29) is computed as the final async step of that side's own `ingest()` and lands in the exact same `setState` call as everything else about that side (name, slides, decision reset) — so "this side's checksum label shows a real 64-hex value, and (after a real upload) differs from what it showed before" is an atomic, race-proof "this side's ingest() has fully completed" signal, unlike a UI element that can render from partial/initial state.
- **When a hosted app already boots with SOME default/demo data (a sample deck, a placeholder record, seeded state), never assume `page.goto()` resolving means that default load is done** — `goto()` only waits for the page's own `load` event, which fires long before React mounts and runs its own async `componentDidMount` work. Any browser-automation script driving such an app needs its OWN explicit "the app's initial data is fully settled" wait before doing anything that depends on a clean starting state, and that wait needs to target something that's provably tied to the FINAL state of that initial load, not merely "some text I expected appeared."

## Trap — destroying a Node HTTP request stream on a validation failure also kills the response (found building `@pptxdiff/server`, this session)
- The first `maxBodyBytes` implementation called `req.destroy()` the moment a streamed request body crossed the configured size limit, then rejected with a 413 error for the route handler to turn into a JSON response. The client never saw that response — only a raw connection reset (`fetch failed` / `UND_ERR_SOCKET: other side closed`). Since Node's `http` server shares one underlying socket between `req` (`IncomingMessage`) and `res` (`ServerResponse`), destroying the request stream tears down the connection the response was going to be written over. Fix: on overflow, stop ACCUMULATING chunks (bounding memory, the actual goal) but keep draining the stream (don't call `req.destroy()`) so `'end'` still fires normally and the handler gets a chance to write a real error response before the connection closes.
- **When rejecting/erroring out of a Node request handler mid-stream, always ask whether the rejection needs to still be ABLE to write a response** — if so, don't reach for `.destroy()` as the reflexive way to "stop the bad request," even though it's the obvious API for "I don't want this data anymore." Caught by a genuine RED test failure (a real `fetch()` call against a real running server, not a mock), not by inspection — this is exactly the kind of protocol-level interaction bug that's easy to miss reading the code and easy to catch by actually making the request.

## Wisdom — a repo-wide `.gitignore` assembled from multiple language templates can silently swallow a same-named directory from an unrelated template (found adding `src/packages/pptxdiff-cli/lib/`, this session)
- This repo's `.gitignore` is generated (`.gitignores/combine.sh` concatenates `js.gitignore` + `py.gitignore` + `user.gitignore`) — and `py.gitignore`'s generic Python-packaging `lib/` rule (meant for virtualenv-style directories) silently matched a brand-new, very much intentional Node source directory (`src/packages/pptxdiff-cli/lib/`, holding real tracked `.js` files) with the exact same name. `git status` just showed the new files as absent, no error, no warning — the kind of gap that's easy to not notice until a commit turns out to be missing files that were clearly `git add`ed. **Whenever adding a new directory in a mixed-language repo with a combined/generated `.gitignore`, run `git check-ignore -v <path>` on it before assuming a plain `git add` will pick everything up** — don't just trust `git status`'s absence of an error. Fixed via a scoped double-negation (`!src/packages/*/lib/` + `!src/packages/*/lib/**` — both are needed; negating only the directory itself doesn't un-ignore its contents) added to `user.gitignore` (the template meant for exactly this kind of project-specific override) rather than hand-editing the generated `.gitignore` directly, which `combine.sh` would silently overwrite on its next run.
- **The inverse gap exists too, found later the same day**: `docs/.scrolls/DOCS.md` §5/§13 claims `src/pptxdiff/docs-site/site/` (the built mkdocs output) is git-ignored — it wasn't; no rule anywhere actually covered it, discovered only because this session ran a real `mkdocs build` for the first time in a while and saw it show up as untracked. A scroll asserting something is git-ignored is not itself evidence that it is — `git check-ignore -v <path>` is the actual check, and it's cheap enough to run reflexively after any command that generates build output in a repo with a hand-assembled `.gitignore`, not just when adding a new source directory.


## Trap — `git config --global` is a flag to the `config` subcommand, not a top-level `git` flag (found building `install-git-integration`, this session)
- `["--global", "config", "key", "value"]` (i.e. `git --global config key value`) is a genuinely invalid invocation — git rejects it outright with `unknown option: --global` and a usage dump. The correct argv shape is `["config", "--global", "key", "value"]` (`git config --global key value`) — `--global` belongs to `config`, not to `git` itself. Found via a real end-to-end test actually running the command against a real temp git repo (`test_git_integration_e2e.mjs`), not by reading git's own docs cold — the pure unit test written alongside the implementation had encoded the SAME wrong assumption in its own expected-output assertion, so it passed right alongside the broken code until the real invocation was tried.
- **A pure unit test asserting the exact shape of an argv array (or any command line) can be just as wrong as the implementation it's checking, if both were written from the same incorrect mental model at the same time.** The unit test alone (`buildGitConfigCommands("global")[0][0] === "--global"`) gave zero warning — it was internally consistent with the bug, not a check against ground truth. Only a genuine end-to-end invocation of the real external tool (`git`, here) surfaces this class of mistake; when building argv for ANY external CLI this project doesn't control, budget for a real invocation against the real tool, not just a pure test asserting your own assumption about its flag syntax.

## Wisdom — testing a feature whose whole point is a real GUI window (found building `difftool`, this session)
- `pptxdiff-cli difftool` deliberately launches a **visible** (non-headless) browser — unlike every other command in this package, there is no meaningful headless version of "open a window for a human to look at" to test instead. `chromium.launch({ headless: false })` fails outright in a display-less sandbox/CI environment (`Target page, context or browser has been closed`, an unhelpfully generic error) unless a display is available — `xvfb-run -a <command>` (Xvfb, an X virtual framebuffer, already present on this environment's image) provides one transparently; a real desktop needs nothing extra since it already has a real display. **Keep tests needing a real display in a SEPARATE npm script** (this project's `test:difftool`, not part of the default `test`) rather than folding them into the main suite — a contributor/CI runner without `xvfb-run` (or on an OS where the concept doesn't apply, e.g. a real desktop that just works) shouldn't have the main test suite fail for an unrelated environment reason.

## Trap — `difftool` window close is not always browser disconnect (found testing real git difftool on macOS/Chrome)

## Wisdom — PowerShell command-mode vs. expression-mode argument parsing (addendum, Chocolatey package session)
- **`SomeCmdlet "a" + "b"` is NOT string concatenation in PowerShell.** Cmdlet/function calls are parsed in "command mode," where `+` between two quoted-string arguments is just another positional argument token, not the binary `+` operator — `Write-Warning "line one " + "line two"` actually passes `Write-Warning` three positional arguments (`"line one "`, `"+"`, `"line two"`), and since `Write-Warning` only accepts one positional `-Message` argument, this throws `A positional parameter cannot be found that accepts argument '+'` the first time that code path actually runs. `throw` doesn't have this problem — it's a language keyword taking a real expression, so `throw "a" + "b"` concatenates correctly. **Rule**: any multi-line message string passed to a cmdlet (`Write-Warning`, `Write-Host`, `Write-Error`, etc.) must be built as a separate variable assignment first (`$msg = "a" + "b"`, which IS expression mode) and then passed as `SomeCmdlet $msg` — never inline `+`-concatenated directly in the argument position. Found while writing `src/packages/pptxdiff-chocolatey/tools/chocolateyuninstall.ps1`, with no `pwsh` available in this sandbox to catch it by running — caught by reasoning through PowerShell's command-vs-expression parsing modes instead. Worth a deliberate second look any time a future session writes/edits `.ps1` files in this repo (currently just the Chocolatey package's `tools/*.ps1`), since there's no automated PowerShell test/lint in this project's CI to catch it otherwise. **Now permanently guarded**: `src/packages/pptxdiff-chocolatey/test_chocolatey_package.mjs`'s `hasCmdletPlusConcatBug()` regex-scans both `.ps1` scripts for exactly this pattern (a `Write-Warning`/`Write-Host`/`Write-Error`/`Write-Output`/`Write-Verbose` call followed by a quoted string then `+`) and fails the build if it's ever reintroduced — demonstrated genuinely RED (reintroduced the bug, confirmed the check caught it) before being restored GREEN, so this doesn't rely on a future session remembering to re-read this note.
