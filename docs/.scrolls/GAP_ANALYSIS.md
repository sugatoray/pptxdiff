# GAP_ANALYSIS.md — Implementation Gaps

Concrete, testable gaps between what SPEC.md describes and a fully "real" implementation. See GAP_CONTEXT.md for the reasoning behind each.

## Rendering fidelity
- [ ] Chart/SmartArt/media parts generated by `sample-pptx.js` are minimal-valid OOXML — not guaranteed to render pixel-perfect in `@aiden0z/pptx-renderer`; some slides may show "Schematic" instead of "Rendered" badge.
- [ ] Master/layout thumbnails are schematic dashed-rect outlines only (position/size of placeholders), not actual rendered master/layout art (background fills, master-level text styles, theme colors are not drawn).
- [ ] No zoom/pan on individual slide previews (only prev/next stepping).

## Diff engine
- [ ] Theme-color (schemeClr) resolution is a hardcoded partial map (tx1/dk1/tx2/dk2/bg1/lt1/accent1 only) in `readRunFmt` — other scheme colors (accent2-6, hlink, folHlink) fall back to the shape's existing color rather than resolving the real theme value.
- [ ] Table cell formatting diff is capped at 6 shown differences + "+N more" note — no way to see all of them without exporting.
- [ ] Animation diff is a single signature-string comparison (type:target:preset joined) — doesn't diff individual animation *parameters* (duration, delay, motion path coordinates).
- [ ] No diff for: slide size/aspect ratio changes between decks, section headers (`p:sectionLst`), custom shows, comments embedded in the original pptx (PowerPoint's own comment feature, distinct from this tool's reviewer comments), OLE objects, 3D models, ink/drawing annotations.
- [ ] Hyperlink diff only covers text-run hyperlinks (`a:hlinkClick` on `rPr`) — not shape-level click-through hyperlinks (`a:hlinkClick` on `nvSpPr`/`cNvPr`) or hyperlinks on images/tables.

## Deck-level comparison
- [ ] `alignSlides`/`refineMoves` similarity threshold (0.12 match / 0.55 move) is a fixed heuristic — no tuning UI, and untested against real-world decks with many near-duplicate slides (e.g. templated report decks) where it may misalign.
- [ ] No detection of duplicated slides (same slide appearing twice in one deck) — alignment assumes roughly 1:1 content uniqueness.

## Reviewer workflow
- [ ] Merge plan is an *export* (JSON of choices) — there is no mechanism to actually apply the merge plan back into a new `.pptx` file. Full OOXML round-trip merge is unimplemented.

## Exports
- [ ] "Shareable link" is a self-contained `data:` URL copied to clipboard — NOT a real short/hosted link. Large decks could produce a very long URL (no size-limit handling/warning).
- [ ] Slack export is clipboard-only plain text — no real Slack API/webhook integration (would need OAuth + a backend, out of scope for a client-only DC).
- [ ] Email export uses `mailto:` — body length is subject to browser/OS mailto length limits; no truncation warning for large reports.
- [ ] No PPTX-native export of the diff overlay (e.g. an annotated copy of the After deck with change highlights baked in as shapes).

## Transitions
- [ ] "Transition preview" is a simplified generic crossfade swatch, not a per-type accurate animation (push/wipe/etc. all look the same motion-wise; only the label text differs).

## Testing / fixtures
- [ ] Red/Green TDD sample deck covers most categories but NOT: hyperlink-on-shape (only on text run), duplicate slides, section headers, OLE objects, real (non-dummy) audio/video content, theme-color (schemeClr) diffing beyond the basic map.
- [x] No automated test harness -- CLOSED (partial): an in-browser self-test suite (runSelfTests, triggered by a button) now covers the core algorithms plus a real merge-export round trip. Not a standalone CI-runnable suite.
- [x] `gen-sample-pptx.mjs` no longer shares a spec with `buildSample()` in `index.html` -- SUPERSEDED/CLOSED (by rewrite): the script was fully rewritten to use `pptxgenjs` instead of `sample-pptx.js`, with its own independent (simplified) shape spec. The "manually-kept-in-sync copy" drift risk described here no longer applies since there's no longer a copy relationship at all — see the new gap below for what this rewrite doesn't cover instead.
- [ ] The on-disk `docs/assets/sample_*.pptx` fixtures (via `gen-sample-pptx.mjs`/`pptxgenjs`) do NOT exercise: SmartArt/diagrams, slide transitions, embedded fonts, real video/audio media. `sample-pptx.js`'s original attempt at the first of these (invented `<a:root>` root element instead of `dgm:dataModel`, missing Content-Types Override, a `dgm:relIds` graphicFrame whose four required relationship attributes all aliased one `diagramData`-typed relationship) is confirmed to break real Microsoft PowerPoint (file becomes unopenable, not even repairable) — and removing just that one defect was NOT sufficient to make the old generator's output open in real PowerPoint either, which is why the whole generator was replaced rather than patched further. `pptxgenjs` has no API for SmartArt, transitions, or embedded fonts at all (confirmed via its type definitions), and real video/audio media embedding would require sourcing/shipping actual valid media bytes (not attempted). The in-browser "Reset to sample" deck (unchanged, still uses `sample-pptx.js`) still covers all four categories for its own narrower purpose (own tolerant parser/renderer, never downloaded as a real file).

## Newly identified gaps (this session)

This is NOT a bug to silently fix — a real fix requires a backend, which is out of scope unless requested.

## Newly identified gaps (this session)

## Offline capability (newly identified gaps, this session)
- [ ] `pdfjs-dist` (an optional peer dependency of `@aiden0z/pptx-renderer`, used only to render embedded PDF objects inside a slide) is loaded via a runtime-constructed `import(pdfjsUrl)` string inside a Web Worker and was NOT part of this app's dependency set even before vendoring -- it remains unvendored and would fail offline if a `.pptx` ever contained an embedded PDF object exercising that code path. Narrow, pre-existing, not a regression from this session's vendoring work.
- [ ] The vendored Spectral font only includes the "latin" Unicode-range subset (matching the app's English-only UI) -- non-Latin text typed into comments/reviewer names/etc. will fall back to the browser's default serif font instead of Spectral's cyrillic/vietnamese/greek glyph coverage that the original Google Fonts CDN link would have served. Purely cosmetic (Spectral is only used for the `h1`/headings, not body text), not a functional gap.
- [x] `test_offline_capable.mjs`'s CDN-host scan was a fixed list of known hosts scanned for total absence -- SUPERSEDED (not just closed): rewritten as a per-swap-point check (see "PPTXDIFF_LITE_MODE" below) since CDN URLs are now a legitimate, gated, opt-in part of the source rather than something that should never appear at all.

## PPTXDIFF_LITE_MODE (newly identified gaps, this session)
- [ ] The env var only works through `bin/cli.js` (Node has env access; a browser doesn't) -- the "just open `index.html`"/VS Code extension paths have no way to trigger lite mode except manually appending `?lite=1` to the URL. Documented, not a bug -- see SPEC.md §25/GAP_CONTEXT.md for why this is the correct design given the constraint, not an oversight.
- [x] No UI affordance (banner/toggle) inside the app itself indicating lite mode is active -- CLOSED: an explicit "Offline Mode" corner toggle (top-right, distinctly separate from the toolbar) now shows and controls the current state in-app, per an explicit follow-up ask. See SPEC.md §25.
- [ ] `?lite=1` is all-or-nothing across all 5 vendor swap points (React, ReactDOM, Babel, JSZip, pptx-renderer, font) -- no way to mix (e.g. vendored React but CDN pptx-renderer) without hand-editing the source. Not requested; a single flag matches the actual use case (A/B against unmodified upstream, or explicitly wanting fresher CDN builds) better than partial mixing would.
- [ ] The in-app "Offline Mode" toggle's OFF (CDN/lite) rendered state — track color, thumb position, `aria-checked="false"` — was not confirmed in a live, fully-booted browser in this dev sandbox, since `?lite=1` can't complete a real boot here (the same outbound-proxy blocking noted elsewhere). The underlying logic is the identical one-line ternary pattern already proven correct for `LIB_URL`/`REACT_URL`/etc., and the ON state (default) was fully E2E-verified, but a from-scratch visual confirmation of the OFF state specifically is still owed on a machine with normal internet access.
