# GAP_CONTEXT.md — Why the Gaps Exist

Maps to GAP_ANALYSIS.md sections. Explains *why* each gap was left, so a future session doesn't "fix" something that was a deliberate scope call — or knows exactly where to pick up if it wasn't.

## Rendering fidelity
- **Chart/SmartArt/media minimal OOXML**: building fully spec-compliant chart/diagram/media parts (with all rels, style parts, quickstyle/colors XML for SmartArt, real codecs for video/audio) is a multi-day effort matching a small slice of PowerPoint's own writer. We built just enough for our OWN diff parser to read reliably; the third-party renderer library rendering them faithfully was a bonus, not a requirement — it gracefully falls back to schematic mode, which was accepted as good enough for a *diff* tool (the point is spotting differences, not perfect visual fidelity of every fixture slide).
- **Master/layout schematic-only**: `@aiden0z/pptx-renderer`'s public API (`renderThumbnailToContainer`) targets *slides* — there's no supported entry point to render a bare `slideLayout`/`slideMaster` part standalone (it has no "slide" context: no theme-resolved placeholder inheritance chain hooked up for a layout in isolation). Reverse-engineering that render path was judged out of scope relative to the ask ("show slide master thumbnails") — a geometry schematic satisfies "show what the layout looks like structurally" without needing to fork/extend the renderer library.
- **No zoom/pan**: never explicitly requested; prev/next stepping was deemed sufficient for a review tool where the main content lives in the diff list, not deep slide inspection.

## Diff engine
- **Partial schemeClr map**: PowerPoint's effective theme-color resolution depends on the *color map* (`clrMap`/`clrMapOvr`) which can remap tx1↔dk1 etc. per slide/layout/master, plus accent1-6 from the theme's `clrScheme`. Building a fully correct resolver requires threading the resolved theme + color map through every shape parse — doable, but adds meaningful complexity for a feature (exact theme-color diffing) that's a rarer edit pattern than direct RGB color changes, which ARE fully diffed already.
- **Table diff capped at 6**: an explicit UI/scope decision to avoid an exploding diff list on large tables — the assumption is a user editing table formatting extensively will re-review the whole table visually rather than read 40 individual cell-diff rows. The cap can be raised or made configurable if requested.
- **Animation diff is a signature string**: animations were the last of ~15 requested diff categories in one message; a full per-parameter animation diff (timing curves, motion paths) is disproportionate effort relative to how often animation *parameters* (vs. presence/type) actually get reviewed in practice. Presence/type/target/order changes are the common case and are covered.
- **No section headers / OLE / 3D / ink**: never requested; these are progressively rarer PowerPoint features. Sections in particular would need `p:sectionLst`/`p:ext` parsing in `presentation.xml` — a contained, addable feature if asked for.
- **Hyperlink diff = text-run only**: shape-level hyperlinks are a distinct XML location (`p:cNvPr > a:hlinkClick` vs. `a:rPr > a:hlinkClick`) that wasn't in the original ask's examples; the text-run case covers the overwhelming majority of real hyperlink usage (linked text, not linked whole-shapes/images).

## Deck-level comparison
- **Fixed similarity thresholds**: chosen empirically against the sample deck's slides (which are deliberately short/distinct) — there was no real-world large deck available to tune against. This is the single biggest risk area for "doesn't work well on my actual deck" bug reports; see PLAN.md for suggested next step (make thresholds configurable, or self-calibrate from the deck's own similarity distribution).
- **No duplicate-slide detection**: the LCS alignment technically CAN match a duplicated slide to either occurrence, but no explicit UI signals "these two are identical duplicates" as a distinct third case — not requested, and would require a different UX (a duplicate isn't added/removed/moved/modified, it's a fourth state).

## Reviewer workflow
- **No persistence**: this is a client-only single `.dc.html` file with no backend/database. Adding persistence would need either `localStorage` (survives reload, not shareable across people/devices) or a real backend (out of scope for a design-component deliverable). LocalStorage was NOT added because reviewer/decision state could easily grow large and the project's editing conventions explicitly warn against silently clearing/overwriting storage that might hold unrelated user data — safer to leave it as clearly-ephemeral in-session state than half-solve persistence.
- **No @mentions/assignment**: not requested; would need a notification delivery mechanism (email/Slack webhook) which requires a backend.
- **No approve/reject rollup UI**: an oversight-turned-backlog-item rather than a deliberate cut — see PLAN.md, this is a good "next small thing."
- **Merge = planning only**: a real merge (writing a new valid `.pptx` that combines chosen properties from both decks) requires a full OOXML *writer* capable of round-tripping arbitrary uploaded files' exact XML (not just our own generated sample format) — effectively building a competitor to python-pptx/OpenXML SDK in browser JS. Explicitly called out as out of scope in the same turn it was requested; the decision-tracking export was offered as the honest, deliverable subset.

## Batch
- **Order-based pairing only**: filename-similarity matching (e.g. fuzzy-matching "Q3-Review-v1.pptx" to "Q3-Review-v2-final.pptx") is a reasonable enhancement but wasn't requested; order-based pairing is the simplest correct default when a user deliberately selects two matched file lists.
- **No batch report export / no progress bar**: batch mode was added in the same turn as several other large features (transitions preview, exports, per-diff approve/reject, three-way merge, moved-slide detection) — time/effort was prioritized across breadth of features over polish of any single one.

## Exports
- **Data-URL "shareable link"**: there is no server component to this deliverable at all (it's a single HTML file). A true shareable link needs *somewhere* to host the report. The data-URL approach is the most honest thing that can be built without inventing a backend — explicitly caveated to the user rather than presented as a real hosted link.
- **Slack/email = clipboard/mailto, not API**: real Slack posting needs an incoming webhook URL or bot token (a secret, which a client-side static file cannot safely hold) — clipboard-copy of Slack-flavored text was the closest honest equivalent.
- **No annotated-PPTX export**: not requested; would require a full OOXML writer for arbitrary uploaded decks (same blocker as real merge).

## Transitions
- **Generic crossfade preview**: implementing per-type accurate previews (push slides left/right, wipe reveals with correct direction, actual PowerPoint easing curves) is meaningful animation-engineering effort for a feature whose main informational value (what transition + what speed) is already delivered as text/data. The animation was added as a "nice visual signal," not as the primary deliverable of that ask.

## Testing / fixtures
- **No automated regression suite**: this is a single-file DC with no test runner wired into the project; verification has relied on the manual/screenshot-based verifier subagent each round. Given the DC authoring model (inline templates, no build step), integrating a JS test framework was never in scope of any single user ask — flagged here as a real gap for long-term maintainability (see PLAN.md).
- **Fixture gaps**: each listed gap (duplicate slides, OLE, etc.) mirrors the diff-engine gaps above — the fixture was built to exercise everything that WAS implemented; it wasn't built ahead of features that don't exist yet.
- **Why `gen-sample-pptx.mjs` copies `buildSample()` instead of importing it**: `buildSample()` is a method on the DC's logic class, defined inline inside `Slide Diff.dc.html`/`index.html` per this project's single-file authoring constraint (WISDOM.md) — there is no standalone module boundary to `import` it from Node. Duplicating the shape spec into a small, separately-runnable script was the pragmatic choice over either (a) refactoring `buildSample()` out into its own importable module (touches the DC's established file layout for a test-fixture convenience, not requested) or (b) hand-writing a different, non-canonical fixture in Python/stdlib (breaks the project's existing "build the parser and the generator together, same data shape" rule — see WISDOM.md — by introducing a SECOND, divergent fixture definition). The accepted cost is the manual-sync gap now tracked in GAP_ANALYSIS.md.
- **Why `jszip` is a devDependency instead of reimplementing zip writing**: `sample-pptx.js` (already shared, already correct, already exercises the exact XML shapes the app's own parser expects) assumes a `JSZip` global — it's the standard, no-need-to-reinvent way to produce a real zip/`.pptx` container from Node. Installed as `--no-save`-style generation-time tooling, not added to the app's shipped runtime (which still loads JSZip from a CDN, per SPEC.md §21's "kept CDN-based" decision — unaffected).

## Accessibility / i18n
- **Not yet audited**: never explicitly requested by the user; standard semantic HTML was used throughout (real `<button>`/`<input>` elements, not divs-with-onClick) which gives a reasonable baseline, but no dedicated a11y pass (aria-labels, focus rings, screen-reader testing) has been done.

## Newly closed gaps (this session) -- why they were tractable now
- Reviewer persistence, notifications, rollup, batch pairing/progress/report, merge writer, self-tests, a11y pass were already on PLAN.md's backlog -- this session worked through it in priority order without new architecture.
- Real OOXML merge writer became tractable because sample-pptx.js's buildPptx and the DC's own parser already share matching field shapes (a WISDOM.md principle) -- slideToBuildSpec is a thin adapter, not a new writer. Our writer can only reproduce what OUR parser extracted (text/tables/background/notes/transitions); images/charts/SmartArt are dropped, honestly, in the export.
- Self-tests are partial-closed deliberately: a real CI-integrated runner isn't possible in a single .dc.html file with no build step. An in-browser suite triggered by a button was judged the honest maximum.
- Accessibility is partial-closed deliberately: a full audit is much larger than adding aria-labels to the highest-value controls, which were done; a full pass remains future work.

## Open bug -- no root cause identified yet
The "nothing visible" report is not yet understood. Ruled out: the diff/render logic itself (renderVals runs cleanly against real sample data in an isolated harness). Suspected but unconfirmed: the async lib-loading Promise.all in componentDidMount hanging rather than throwing -- a hang would not be caught by the existing try/catch (which only handles rejections, not a promise that never settles), and would explain why the whole iframe was unresponsive to eval_js. Plausible but unverified -- next session must confirm with _probe.html before treating it as the fix target.

## Why the MOVED-tag bug took two rounds (this session)
The first fix (patience-sort LIS) was a genuine improvement in KIND (global property instead of local heuristic) but not in CORRECTNESS for ties -- patience sort finds *a* longest increasing subsequence, not *the* one a domain cares about, and when multiple LIS candidates of equal length exist it silently picks based on processing/insertion order, which is arbitrary from the user's perspective. The verifier caught this with a concrete counter-example (decreasing bIdx pair, two length-1 chains) rather than accepting the first fix as sufficient. The real fix required deciding WHICH tie-break the domain wants (prefer same-position pairs as 'not moved') and encoding that as a secondary DP dimension -- a reminder that 'a correct-looking algorithm' and 'the algorithm that matches user expectations on ties' are not automatically the same thing.
## Why keyboard shortcuts and collapse-all were straightforward
Both reuse fully-existing methods (move, setDecision, setView, togglePairCollapse) -- no new business logic, just new entry points into it. This is why they shipped in the same turn as the much harder MOVED-tag fix.
## Why merge-winner preview is read-only for now
Letting the user override a winner directly from the preview panel would need either a new per-slide-level merge override (separate from the existing per-diff Keep-Before/After picks) or a way to bulk-flip all of a slide's diff picks from one click -- neither was asked for; the preview's job was narrowly to show what WOULD happen before committing, which it does.

## Why Notion/Confluence exports are downloads, not live pushes
Same reasoning as the existing Slack/email/share-link exports (SPEC.md §6): this is a single client-side .dc.html file with no backend to hold API credentials (Notion integration tokens, Confluence API tokens/OAuth) safely. A real push would need a server-side proxy at minimum. The chosen approach -- generate the exact content format each tool's own import feature expects (Markdown for Notion, wiki markup for Confluence) plus a toast telling the user the next manual step -- is the most honest maximum achievable without inventing a backend.
## Why touch reorder doesn't have a drag-preview
Native HTML5 drag-and-drop's ghost-element preview is a browser-provided feature tied to the dragstart/dragover event pair, which doesn't fire on touch. Building an equivalent visual (a floating clone following the finger) is a real but separate enhancement -- not requested, and the reorder itself works correctly without it (row-swap happens on touchend based on the row under the finger at release).

## Why live push was built as "real but likely to fail" rather than skipped
The user explicitly asked for live push to three specific services. Building it as a real fetch-based attempt (rather than refusing outright) is more honest than either (a) silently only offering the file-based fallback again, or (b) pretending it works. Each service's actual CORS behavior differs in practice: Slack webhooks are the one case where a client-only workaround (form-encoded no-cors POST) is a well-known, commonly-used pattern that DOES work from a browser; Notion and Confluence's REST APIs are designed for server-side/OAuth-app use and typically reject direct browser-origin calls. The code path is real and correct for all three — whether it succeeds depends on the target service's CORS policy at push time, which can change, hence 'attempt for real, catch and explain' rather than not implementing it at all.
## Why import is overwrite-only for now
A merge UI ("this import has decisions for slides you've also already reviewed differently — which wins?") is a real, separate feature that wasn't asked for. Overwrite-only was the simplest correct behavior for the common case this shipped for: restoring a prior review session's state on a fresh page load, where there IS no conflicting in-progress state yet.

## Why Slack's delivery confirmation is still only partial
A hidden iframe's `load` event fires whenever the browser receives ANY HTTP response (200, 404, 500 all trigger `load`, not `error` -- `error` is reserved for network-level failures like DNS/connection refusal). Reading the actual response status code cross-origin is blocked by the same-origin policy regardless of iframe vs fetch. True per-status confirmation requires either a backend proxy (out of scope, no server exists) or Slack changing their webhook CORS policy. The current fix is a genuine, real improvement over the prior no-cors fetch (which had ZERO signal, not even network-level) -- it's honestly communicated as 'the request round-tripped, please verify in the channel,' not oversold as a true delivery receipt.
## Why mergeReportPatch's conflict rule isn't configurable
The ask was specifically 'merge/overwrite choice,' which those two buttons deliver. A THIRD dimension (whose side wins on conflict, independent of merge-vs-overwrite) wasn't requested and would double the decision surface in the choice modal for a scenario (importing a MORE authoritative file over your own less-authoritative in-progress work) that's plausible but speculative -- Overwrite already covers 'I want the import to fully win' when that's genuinely the intent.
## Why credential persistence is all-or-nothing
A single opt-in checkbox covering all fields was the simplest safe default matching the ask ('persist to localStorage (opt-in) / session only (current)') -- per-field granularity is a real but more complex UI (checkboxes per field, or per-service) that wasn't requested and adds surface area for a feature whose main risk (secrets sitting in localStorage) is already fully mitigated by the all-or-nothing opt-in itself.

## Why DUPLICATE is same-deck-only
The original ask (and the existing findDuplicateSlides helper it builds on) was specifically about slides duplicated WITHIN one deck ('duplicate-slide 4th alignment state' alongside added/removed/moved/modified, which are all about relationships BETWEEN the two decks — duplicate is the one alignment-adjacent fact that's actually an INTRA-deck property). Cross-deck near-duplication (a Before slide resembling a different After slide) is really just what the alignment/similarity engine already does for matching — extending 'duplicate' to also flag near-duplicate CROSS-deck slides that DIDN'T align to each other would overlap confusingly with the existing move-detection semantics, so it was kept scoped to the same-deck case that was actually asked for.
## Why the merge-choices/diffDecisions used by the export-merge feature aren't touched by report import
parseReportForImport/mergeReportPatch operate on the REVIEW state (decisions, comments, history, UI state) — the separate three-way-merge feature's per-diff Keep-Before/After/Custom picks (`mergeChoices`) and merge-winner overrides for the .pptx export live in a conceptually different area (content-merge decisions, not review decisions) and were out of scope for the original 'report-JSON round-trip import' ask, which was about restoring a REVIEW session, not a content-merge plan.

## Why cross-deck duplicate detection excludes already-aligned pairs
If a Before slide and its own matched After partner are similar, that's just... a matched pair (possibly IDENTICAL or CHANGED) — not a 'duplicate' finding, which is specifically for content appearing in a place the alignment DIDN'T connect it to. Excluding aligned pairs via the `alignment` parameter keeps the note panel meaningful (only surprising/unexpected similarities) rather than restating every normal match.
## Why reviewer bulk-remove has no confirmation dialog
Consistent with the rest of this app's direct-manipulation style (single-reviewer remove is also immediate, no confirmation) — adding a confirmation specifically for the bulk case would be an inconsistent interaction pattern. Not requested; flagged here in case real usage shows it's needed.

## Why only bulk reviewer removal got a confirmation step, not bulk comment/history
The explicit ask was specifically 'confirmation for bulk reviewer removal' — the other two bulk-select features (diff list, comments, history) were a SEPARATE ask ('select-all/none for diff list/comments/history') with no confirmation requirement attached. Removing a reviewer is arguably higher-stakes (loses attribution/identity, not just content) which may be why it was singled out; comments/history deletion, while also destructive, wasn't asked to be gated. Keeping the distinction narrow (exactly what was asked) avoids inconsistently second-guessing which other actions 'should' also be confirmed without being asked to do so.
## Why history selection uses a content signature instead of an index
The history array can already be mutated (filtered via `clearSelectedHistory` itself, or in principle re-sorted) — an index-based selection key would silently point at the wrong row after any such mutation. A content signature (timestamp+reviewer+action+label+note) is stable across reorders and was already established as the de-dup key in `mergeReportPatch` from a prior session, so reusing it here avoids introducing a second, inconsistent identity scheme for the same data shape.

## Why single-comment delete has no confirmation despite being unrecoverable
The ask was specifically for confirmation on the BULK paths (bulk comment delete, bulk history clear) — single-item delete across this whole app (reviewer chip, batch file, and now single comment) has consistently been immediate/unconfirmed by design, and introducing confirmation for exactly one of these single-delete actions (comments) while leaving the others immediate would be a more confusing inconsistency than the current one. If confirmation-on-every-delete is wanted, that's a broader design change to raise explicitly, not an incidental addition here.
## Why replies have no delete capability yet
Not requested. Comments themselves only gained delete capability this session and the prior one; replies are a nested one-level-deeper data shape (`comment.replies[]`) that would need its own selection/delete key scheme (e.g. `pairKey:commentIdx:replyIdx`) — a reasonable next step but out of scope for the specific single-comment-delete ask.

## Why single-comment-delete confirmation reverses a prior explicit decision
Last session deliberately kept single-comment delete immediate, reasoning that confirming exactly one single-delete action (comments) while leaving others (reviewer chip, batch file) immediate would be MORE inconsistent than the status quo. This session's explicit ask ('add confirmation before single comment delete... AND batch file removal') resolves that inconsistency concern by confirming BOTH at once, in the same turn -- so the original objection no longer applies. This is why doc updates matter: GAP_CONTEXT.md's reasoning was correct for its moment but needed to be revisited once the actual ask changed the premises.
## Why 'Clear all decisions' doesn't scope by reviewer
Not requested. The ask was for a generic 'clearing all decisions' action; scoping it to one reviewer's votes specifically is a plausible but separate feature (it would need its own UI for 'whose votes' and its own confirmation copy) -- flagged as a gap rather than assumed.

## Why the shared confirmation modal is a single data-driven block, not a child DC
This project's authoring conventions set a high bar for splitting into child DCs (only when a UI element repeats 4+ times across SCREENS with real props/state, and even then, users typically duplicate a DC file to riff on it rather than share children). A confirm modal that appears in EXACTLY ONE place at a time, driven by one piece of state, doesn't meet that bar -- the right level of reuse here is a single template block reading a runtime-computed data object (`pendingConfirm`), which is what was built. This mirrors how the app already handles other single-instance-but-many-triggers UI (e.g. the toast).
## Why 'Specific slide range' uses All-pairs row position instead of Before/After slide numbers
Before and After decks can have different slide counts and orders (that's the whole point of alignment/moved-slide detection) -- there is no single 'slide number' that unambiguously identifies a PAIR once slides have been added/removed/reordered. The All-pairs view's row order is the one stable, already-displayed ordering a user can visually reference ('the 3rd through 5th rows I see on screen'), so range inputs use that position rather than inventing a new numbering scheme.

## Why the sensitivity/ignore-list settings are global, not per-context
Cross-deck duplicate detection already runs from three call sites (deck-level note panel, merge preview, batch mode) sharing the same underlying pure function -- giving each context its OWN threshold/ignore-list would mean either three separate state slices (more surface area, confusing when they disagree) or a context parameter threaded through every call (more complexity for a use case -- 'I want batch mode looser than the main view' -- that wasn't requested). One shared setting keeps the mental model simple: 'what counts as a near-duplicate' is one decision, not three.

## Why the npm CLI opens a browser tab instead of a real native window
User was asked directly (CLI+browser vs. Electron vs. Tauri) and picked CLI+browser. Electron ships ~150-250MB installers per OS and needs code signing to avoid Gatekeeper/SmartScreen warnings; Tauri is smaller but needs a Rust toolchain to build. A stdlib-only Node http server + `open`/`start`/`xdg-open` gets the "one command, app opens" experience with none of that build/signing surface, at the cost of not being a real windowed app. Revisit if a genuine native-window feel (dock icon, no browser chrome) is explicitly requested.
## Why the npm CLI still requires internet access (not vendored for offline use)
User was asked directly (keep CDN-based vs. vendor everything for offline) and picked keep CDN-based, matching how the app already worked before packaging. Vendoring React/ReactDOM/Babel-standalone/JSZip/pptx-renderer plus self-hosting fonts is real engineering effort (and ongoing maintenance to track upstream versions) for a benefit (air-gapped use) that wasn't the ask. The CLI's local server changes nothing about the app's existing CDN dependency, it only changes how `index.html` gets opened.
