## Update (2026-07-21 — fixed off-slide element bug in the pptxgenjs fixture generator)
- **Bug**: after switching to `pptxgenjs` (see update below), the user reported elements in `sample_*.pptx` render outside the slide bounds. Root cause: `pptx.layout = 'LAYOUT_16x9'` is pptxgenjs's built-in preset, which is **10 x 5.625in**, NOT the 13.333 x 7.5in modern PowerPoint widescreen size every coordinate in the script was authored against (confirmed via `unzip -p file.pptx ppt/presentation.xml | grep sldSz` showing `cx="9144000" cy="5143500"` = 10x5.625in, vs. the expected `12191695 x 6858000` = 13.333x7.5in). Nearly every shape's `x`/`y`/`w`/`h` therefore extended past the actual slide edges.
- **Fix**: `pptx.defineLayout({ name, width: 13.333, height: 7.5 })` + `pptx.layout = 'PPTXDIFF_16X9'` — a custom layout matching what the coordinates actually assume, instead of relying on the built-in (differently-sized) preset name. Also fixed a real leftover bug the linter caught: the slide-1 footer had `isBefore ? 'Confidential — 2026' : 'Confidential — 2026'` (identical text both branches, a copy-paste leftover from an earlier edit) — simplified to a plain string.
- **New permanent guard**: added `checkBounds(label, {x,y,w,h})`, called via `placedText`/`placedImage`/`placedTable`/`placedChart` wrappers at every element-placement call site — throws immediately at generation time if any shape's bounds exceed the slide's declared width/height. This is exactly the kind of non-trivial position-arithmetic logic (WISDOM.md/ponytail conventions) that needs a standing check, not just a one-time fix; it will catch a repeat of this exact mistake (or a future coordinate typo) before a file ships.
- **Verified**: `uv run --with python-pptx` — walked every shape in every slide of both regenerated files and compared `shape.left/top/width/height` against `presentation.slide_width/slide_height`; **zero out-of-bounds shapes** on either file (down from the wrong-canvas-size bug). Content-type/relationship audit (same technique as the earlier SmartArt incident) still comes back clean. Slide size confirmed correct: 13.333 x 7.5in.
- Also refactored `buildDeck()` into per-slide helper functions (`buildSlide1`/`buildSlide2`/`buildSlide3`/`simpleSlide`) — was flagged by the linter for excess cognitive complexity as one large function; splitting it also made the bounds-check wrapper straightforward to apply consistently at every call site.

## Update (2026-07-21 — fixed real-PowerPoint corruption in the static fixtures; SmartArt dropped from export) — SUPERSEDED, see update above
- **Bug**: the first version of `docs/assets/sample_*.pptx` (built by `gen-sample-pptx.mjs`) would not open in real Microsoft PowerPoint ("cannot even repair"). Root cause found via `python-pptx`/`uv run --with python-pptx`: `sample-pptx.js`'s SmartArt output is placeholder XML, not real OOXML — the diagram-data part's root element is an invented `<a:root><a:t>...</a:t></a:root>` (not a real `dgm:dataModel`), its Content-Types entry falls back to generic `application/xml` (no Override), and the `dgm:relIds` element on the graphicFrame points ALL FOUR required relationship attributes (`r:dm`/`r:lo`/`r:qs`/`r:cs` — dataModel/layout/quickStyle/colors) at the SAME single relationship, typed only as `diagramData`. This is unambiguously invalid per ECMA-376, independent of any particular reader's leniency — it was only ever "valid enough" for this app's own bespoke parser (see WISDOM.md's "just enough for OUR OWN parser" line, which undersold how far from spec it actually is).
- **Fix, scoped narrowly**: `gen-sample-pptx.mjs` now OMITS `smartArt` from its copy of the sample shape spec (redA/redB/greenSpec) — everything else (text, images, tables, charts, hyperlinks, notes, transitions, backgrounds, embedded fonts, video/audio media) is unaffected and validates clean. `index.html`'s in-browser `buildSample()` is UNCHANGED and still includes SmartArt — it's harmless there because that buffer is only ever consumed by this app's own tolerant parser/`pptx-renderer`, never downloaded as a real file. This is now a deliberate, documented divergence between the two copies (see GAP_CONTEXT.md).
- **How it was verified**: `uv run --with python-pptx python3 ...` — opened both regenerated files, walked every shape/chart/table/notes object without exception, and confirmed via the low-level `pptx.opc.package.OpcPackage` API that every part has a real (non-generic) content type and every relationship resolves. Also re-checked `unzip -t` (valid zip) and grepped for any leftover `dgm:relIds` (none). **Not yet confirmed by actually opening in the Microsoft PowerPoint app itself** — automating that app's GUI was explicitly declined this session in favor of the python-pptx approach; if a repair prompt still occurs, treat SmartArt as ruled out and look next at the embedded font relationship (`p:embeddedFontLst` + `.fntdata` parts contain random bytes, not real TrueType data — lower suspicion than SmartArt since it's a referenced binary blob rather than inline shape-tree XML, but not proven safe either).
- **Process note for future sessions**: `python-pptx` opening a file successfully is necessary but NOT sufficient evidence that real PowerPoint will accept it — python-pptx doesn't validate OOXML against the actual XSD schemas and has no model for SmartArt/diagram parts at all, so it silently tolerated the exact same file real PowerPoint rejected. The decisive signal here was manually inspecting `part.content_type` for every part (via `OpcPackage.iter_parts()`) and catching the generic `application/xml` fallback, plus reading the actual diagram-data XML content by hand. Prefer this content-type + raw-XML inspection technique over trusting "python-pptx opened it fine" alone when validating fixtures meant for real Office compatibility.

1. **compareImage crash** — used shapeLabel(a) (expects .paras) on image objects. Fixed: use a.name directly.
2. **Master/layout panel blank names** — layoutBox() fallback + try/catch hardening around every per-slide sub-parser.

7. **MOVED tag inverted (this session, two rounds to fix)** — round 1 replaced the local leftover-pass heuristic with a patience-sort LIS, which was an improvement but still arbitrary on ties (decreasing bIdx sequences with two length-1 chains): it kept whichever chain the sort processed last, which happened to be the wrong one. Round 2 fix: replaced patience-sort with an O(n^2) DP that tracks a secondary same-position (aIdx===bIdx) count per chain and tie-breaks on it when reconstructing the best chain — verified via a direct unit test (`markMovedByLIS` regression test) reproducing the exact 5→5-vs-6→4 tie case. **Lesson: LIS/patience-sort is not just "find *a* longest chain" when the semantic meaning of ties matters — when two equally-long chains exist, be explicit about which one the domain prefers, and encode that preference into the DP's comparison rather than relying on insertion-order behavior of a generic algorithm.**
