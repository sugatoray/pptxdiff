## Update (2026-07-31 — parser-independent SHA-256 content checksum in every diff export)
- User asked for the diff exports (all formats) to include a checksum of the .pptx CONTENT, explicitly not a raw file hash (flagged timestamp info as the reason). Agreed and recommended hashing this app's own parsed slide structure instead — a genuinely nice property (same hash ⟺ diff engine finds zero differences) for zero new zip-reading code. User read it over and explicitly redirected: "I would prefer the parser independent path. Can you use something like OpenSSL?"
- **Answered the OpenSSL question directly before implementing**: this app has no backend/shell access by design (WISDOM.md Constraints), so literally invoking the `openssl` binary isn't possible from the client-side code path — but SHA-256 is a standardized algorithm, so `crypto.subtle.digest('SHA-256', ...)` and `openssl dgst -sha256` produce byte-identical output for the same bytes, preserving the actual property wanted (standard, tool-independent, externally verifiable).
- **Implementation**: `computeContentChecksum(buf)` reads the raw zip directly via JSZip (already vendored) — genuinely independent of `parseBuffer`/`parseSlide`/this app's own semantic parser. SHA-256s every part's raw decompressed bytes except `docProps/core.xml`, `docProps/app.xml` (save-timestamp/edit-session metadata, never content) and `docProps/thumbnail.*` (derived preview image, not authored content, not guaranteed deterministic across saves/tools) — sorts remaining parts by path (determinism regardless of zip entry order), SHA-256s the resulting `"path:hash\n"` manifest as the final checksum. New pure `isExcludedFromContentChecksum(path)` predicate. Computed once per side in `ingest()` (`contentHashA`/`contentHashB` in state), read synchronously by every export — no export re-derives it.
- **Surfaced everywhere**: a new always-visible "Content checksums" panel in the app (feeds PDF/print for free, since that's just `window.print()` of the live page), plus `buildJsonReport()` (`contentChecksum: {algorithm, before, after}`, also flows into the shareable link's embedded JSON), `exportHtmlReport()`, `buildMarkdownBody()` (Markdown/Notion), `buildConfluenceWikiMarkup()`, `buildPlainSummary()` (Slack/Email), and the shareable link's human-readable body.
- **Honest handling of the one real gap**: `crypto.subtle` needs a secure context (fine under the CLI's `http://localhost`, not guaranteed under the `file://` direct-open launch path). Added `this.cryptoSubtleAvailable` (checked once at boot, a plain instance field not state) so the UI can correctly distinguish "still computing" from "genuinely unavailable" instead of showing a misleading permanent "computing…" — `computeContentChecksum()` never throws, returns `null` in that case, and every export shows "unavailable" rather than a wrong/fabricated hash.
- **Testing**: 7 new assertions for `isExcludedFromContentChecksum` (both directions, plus a same-named-file-outside-docProps/ edge case), plus `computeContentChecksum` tested against synthetic JSZip fixtures with precise control — same "slide content," different `docProps/core.xml`+`app.xml` timestamps → identical hash; genuinely different slide content → different hash; `crypto.subtle` forced unavailable → graceful `null`, not a throw. Self-test count 119 → 130. Demonstrated genuine RED→GREEN: temporarily made the exclusion predicate always return `false`, confirmed exactly 5 dependent assertions failed (125/130, everything else stayed green), restored it, confirmed 130/130.
- **Verified end-to-end against the real running app, with a real (not just synthetic) timestamp-independence proof**: all 7 export formats (JSON/HTML/Markdown/Confluence/Slack/shareable-link-page/shareable-link-embedded-JSON) show the identical, correctly-computed checksums for the loaded sample deck. Clicked "Reset to sample" — which regenerates the `.pptx` files from scratch via `buildPptx()`, stamping a fresh timestamp each time — and confirmed the checksum panel shows the EXACT SAME hash before and after, against the app's real file-generation path rather than only hand-built test fixtures.

## Update (2026-07-30 — security hardening P0 ticket 3: path.relative()-based static-file path containment)
- Picked up `docs/.scrolls/SECURITY_HARDENING_PLAN.md`'s third P0 ticket (P0 is now fully closed): `bin/cli.js`'s `filePath.startsWith(ROOT)` was a raw string-prefix check — fooled by a sibling directory sharing `ROOT`'s prefix (`/app/src/pptxdiff` vs. `/app/src/pptxdiff-evil`) and blind to symlinks.
- **Fix**: new pure, exported `isPathContained(root, candidate)` (`path.relative(root, path.resolve(candidate))`, contained iff the result is `""` or doesn't start with `".."`/isn't absolute) replaces the `startsWith` call site.
- **Real finding while writing the test, worth remembering**: traced `path.normalize()`+`path.join()`'s actual behavior before assuming the HTTP layer could reproduce the sibling-prefix bug, and found the pre-fix code already returned `404` (never `200`, never even `403`) for every `../`-style traversal payload tried — `path.normalize()` clamps `..` at an absolute path's leading `/`, and `path.join(ROOT, ...)` doesn't treat a leading `/` in a later argument as an absolute-path reset (unlike `path.resolve()`), so this call site's specific construction already prevented `../` escape by construction, regardless of which containment check gated it. The sibling-prefix weakness this ticket actually closes is only reachable by calling `isPathContained()` directly with a crafted sibling path — the HTTP layer's `path.join(ROOT, ...)` construction can never literally produce a `ROOT`+`"-evil"` string. Lesson: don't assume a documented weakness is exploitable through every call site that uses the flawed check; verify empirically (here: a plain `node -e` trace) before writing a test that asserts something that isn't actually true of the specific code path.
